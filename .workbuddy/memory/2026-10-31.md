# 2026-10-31

## 第十七轮：专精基线表（解决「换职业就错」）

### 起因
用户质疑：现在只有拿对应角色的数据才能算准，换职业就错，"核心卖点是属性计算，算不准没人用"。
问 Raidbots 怎么解决。附带给了生存猎人两张面板截图（换了一件装备）。

### 查 SimC 源码的结论（重要，推翻了一个常见误解）
- SimC 有 40 个专精子类，但**属性换算一行都不在里面**。`composite_spell_crit_chance()`
  在 `player.cpp` 基类，40 专精共用，结构是「基础值 + 评级换算 + buff」，没有 switch(spec)。
- 专精差异只有两个维度：①`_mastery = find_mastery_spell(spec)->effectN(1)` 一个查表指针
  ②`get_passive_player_value()` 扫被动累加。**用数据表达差异，不用代码表达**。
- 所以我们的答案：不建 40 个类，建一张表。40 个类意味着改一处公式动 40 处，必然分叉。

### 关键数据（全部来自客户端，不是拟合）
- `engine/dbc/generated/sc_scale_data.inc` 里 `__combat_ratings[24][90]`：
  暴击/精通 46、急速 44、全能 54、吸血 69、闪避 36.8。90 级值 ×100 = 项目里的 base_rate，
  **完全一致**——Maxroll 那份数据其实就是这张表，不是二手拟合。
- 精通系数取法：`spelleffect_data_t::mastery_value()` = `_sp_coeff * 0.01`（第 11 个字段），
  必须 index 0。`专精精通系数表.md` 的取法是对的。
- `dbc::all_crit_base()` 直接 `return 0.05`（注释 "Gametables removed in Legion"）——
  唯一一个不查表不扫被动就确定存在的基础百分比。
- Aura 映射（扫被动时要用）：`A_MOD_ALL_CRIT_CHANCE=290`、`A_MOD_VERSATILITY_PCT=417`、
  `A_MOD_MASTERY_PCT=318`。原料 `__spelleffect_data[53449]` 就在 sc_spell_data.inc 里。
- SimC 数据里**没有** CurvePoint 表（DR 曲线 21024 是 hotfix 数据），也没有
  oct_class_combat_rating_scalar（新版已删）。

### 两张截图的验证（决定性）
生存猎人，风换一件装备：暴击 1033→1084（+51）、精通 1636→1585（−51）、急速/全能不变。
- Δ 法直接定分母：51 评级 / 1.11% = 45.95 → **暴击分母 46 确认**，不依赖任何假设
- 反推基线：crit 15.003/15.005、haste 2.044/2.044、vers −1.004/−1.004、
  mastery 14.003/14.001，**漂移 ≤0.002**（面板两位小数的舍入极限）
- **精通必须走递减**：不打折时基线漂 0.109，加上 1380 那档后收敛到 0.002。
  这把 Maxroll 的 DR 表也验了——之前以为"装备没进递减区，验不出来"，其实 1636 已经进去了。
- 反推的精通点数全是整数：射击/敏锐 8 点（=客户端基础值，没吃天赋），
  兽王 11、生存/守护 14（多的是天赋）。

### 改动
- 新增 `data/raw/spec_stats.json`：5 个专精的基线（命中/急速/精通/全能）+ source + confidence。
  `confidence: low` 的标注了可疑点（守护德精通按 coeff 1.0 算出来是 8.15 不是 9.8）。
- `build_db.py`：新建 `spec_stats` 表；`load_spec_stats()` 比对文件里的 build 和 meta.json 的
  wowBuild，不一致打警告（观测值的失效方式不是"有新版本"而是"天赋改版"）。
- `session.py` 三处：
  1. `_curve_pct` 去掉 `+ mastery_base_points(8)`（全局常数，实测每专精不同）
  2. 新增 `spec_base()` 查表、`flat_source()` 报来路（panel/spec/base/none）
  3. `flat_pct()` = 表铺底 + 面板逐项覆盖；没数据的专精补 5% 基础暴击（`CRIT_BASE_PCT`）
- `set_panel()` 补 `self._flat = self.flat_pct()`——**原来漏了，填完面板百分比纹丝不动**。
- 前端 `render.js`：百分比悬停显示「装备 23.15% ＋ 天赋 15.00%」，CSS 加 `cursor:help` + 虚下划线。
- 文档：data/README 加 spec_stats 性质说明、技术路线改「第三层」整段（含验证过程）、
  wowlib/README 加公式与 flat_source 四态表、build/README 说明它为什么不在版本清单里。
- 测试 254→**260 项**，新增 `group_spec_base()`：表入库、没面板用表、面板逐项覆盖、
  换装备基线不变、精通必须走递减、没数据的专精只补 5% 暴击。

### 遗留
- 只有 5 个专精有基线（猎人三系 + 敏锐 + 守护），35 个没有。两条路：
  ①扫被动（原料齐全，要判 spell 的 class_mask/spec 归属，工作量大）
  ②用户填面板逐步积累（表 + 覆盖的架构已支持）
- 生存 vers −1.00、射击 vers −0.55 反常（不像整数的天赋加成），疑采样时有 buff，待复核。
- 守护德精通系数到底该 0.7 还是 1.0（面板显示的是攻强那条），`spec_mastery.json` 里有矛盾记录。

## 第十八轮：朋友测试前的体验打磨

### 用户决定
不扫被动了，"把现在能做好的做好"，准备把测试版给朋友测各自职业。所以重点不是补数据，
而是**别让朋友被不完整的数字误导**——他导入自己的角色看到暴击 12.74% 而游戏是 20%，
会认为工具不准，这是最容易失去信任的地方。

### 抓到的问题
`renderStats()` 里的 `calibrated = !!Object.keys(s.panel).length` —— **只看"填没填面板"**。
只填了敏捷/耐力、没填百分比的情况下，界面显示"面板值 / 含角色基础"，
但绿字四项仍然是「只算装备 + 5% 暴击」，**界面上一个字都没提**。朋友测必踩。

### 改动
- `render.js`：`calibrated` 旁边加 `pctThin`，逐项看 `flat_source !== "panel"`。
  缺天赋的那项百分比后加金色小星号 `<i class="est">*</i>`，属性栏底部加一行
  「* 绿字只算装备，填「面板校准」可补上天赋」。
  有数据的专精不显示星号（兽王四项无标记，战士四项全带），填了面板星号消失——
  这是给用户的正向反馈。
- 主行文案去重：`职业基础/未含天赋，可校准` → `职业基础值 / 主属性未含天赋`，
  和星号行的"绿字"分工，不重复说同一件事。
- `index.html`：面板校准弹层里百分比那段说明过时了（还写"影响换算率"），
  改成"建议四项都填，不填只能套用专精默认值，你的天赋点法跟别人不一样就会差几个百分点，
  属性栏带 * 的就是这种情况"——和界面上的星号形成闭环。
- `src/web/README.md` 新增「属性栏：数字不全时要看得出来」一节。
- 确认内测包没问题：`package_beta.py` 带 `data/wowgear.db`，`spec_stats` 表就在库里；
  `data/raw/` 不带但运行时不需要（只 build 时读）。

## 第十九轮：版本控制 + 臃肿体检 + 游戏内插件

### 最要紧的发现：项目没有 git
15 轮开发、278 项测试，一次误删就没法回头。已 `git init` + 两次提交（88 文件 / 5.1MB / .git 2.1MB）。
修了 .gitignore 一个真 bug：`data/raw/` 一刀切把**不可重建**的自抓数据也排除了
（spec_stats / spec_mastery / gems / enchants / sockets / rating_curves / class_base / names_zhcn）。
git 规则是「父目录被排除后里面再写 ! 也白搭」，必须先 `data/raw/*` 再逐个放行。

### 臃肿体检（用数据说话）
- Python 12600 行 = 运行时 7200（wowgear+wowlib+server）+ 构建期 3400 + 测试 1400
- 前端 3270 行，文档 2256 行，数据 85MB（入库只 5.1MB）
- 真死代码只有 126 行（talents.py，0 处引用）
- **结论：代码不臃肿**，臃肿感来自「天赋链路」这条和主流程无关的半成品：
  talents.py(126) + fetch_talents.py(204) + talents.json(740KB)
- 建议删除（不是续接）：天赋给的属性已由 spec_stats 基线覆盖（面板−装备天然含天赋），
  留着只会让后来人以为这里差一块。已在技术路线待办里写明。

### 插件方案（核心判断）
用户想「把项目做成插件」。边界的真相：
- 插件**能**读评级/换算/面板总数/装备，能存 SavedVariables，能生成可复制文本
- 插件**不能**联网、不能跑 Python、不能读全装备库（只有客户端缓存过的物品）
→ 所以插件是**数据采集器**，不是替代品。「换上那件会变成什么样」仍在网页端。

关键 API（已查证）：`GetCombatRating(9/18/26/29)` 评级，`GetCombatRatingBonus(同)`
返回该评级换算的百分比（**不含天赋**），`GetCritChance/GetHaste/GetMasteryEffect` 面板总数，
`GetMastery()` 返回精通点数。三样一起给，`T − B` 就是天赋那部分。

### 产出
- `addon/WoWGear/`：WoWGear.toc + Core.lua（约 200 行）+ README。`/wg` 弹框，自动全选复制。
  40 个专精 ID 从 spec_mastery.json 生成，注意 holy/frost/protection/restoration 各两家同名，
  必须配 classID 用。
- `src/wowlib/addon.py`：解析 `key=value;...`，反推基线，cross_check 对比。
  **只信任评级和面板总数**，换算一律用我们自己的公式重算——因为 `B` 的口径不一致
  （精通的 GetCombatRatingBonus 给的是点数增量不是百分比）。
- `tools/import_addon.py`：粘串就出基线，`--write` 落地，**cross_check 不过就拒绝写**
  （防止把错误固化进表）。`--vers` 手填面板值，并打印两种分母的试算结果。
- 测试 278 + 40，新增 group_addon（解析/容错/重名专精/反推基线/校验能抓到偏差）。

### 新疑点：全能分母
插件模拟数据算出──348 评级：分母 54 → 基线 −1.00，分母 64 → 基线 0.00。
而早先兽王 394 → 7.30% 支持 54。两条证据矛盾，必须等真实插件数据定案
（`GetCombatRatingBonus` 给的是游戏自己的答案）。已写进技术路线待办第 2 条。

### 未做
- 网页端的「导入插件数据」入口（现在是命令行）
- 插件未实测：API 名称按文档写，个别可能有出入，需要用户进游戏跑一次

## 第二十轮：导出被 Raidbots 拒绝（真 bug，根因在 simc 源码里）

用户报：换了头部后导出 simc，Raidbots 报 `"Load from SimC Addon" input is not valid`。

### 排查顺序（先证明不是别的地方）
1. 未改动时导出与原文**逐字节相同**（7255 字节，checksum d5ed75c8 一致）→ 搬运逻辑和 adler32 都没问题
2. 改动后 diff 只有 2 行：head 行 + checksum 行 → 问题在这
3. 前端只是 `textarea.value = d.simc` + `writeText`，没加工 → 排除前端

### 真凶：装备行写了名字
`engine/item/item.cpp:1581`
```cpp
if ( ! option_name_str.empty() && ( option_name_str != name_str ) )
{
  sim -> error( "... has inconsistency between name '{}' and '{}' for id {}", ... );
```
`sim->error` 让整个模拟失败。Raidbots 跑 simc，失败 → "input is not valid"。
**游戏插件因此才只吐 `head=,id=271492`**：中文客户端的名字 simc 必然不认。
我们 `_simc_line` 里 `parts = [(item.name or "")...]` 好心补英文名，正好踩雷。

### 顺带确认的：ilevel 合法
simc 自己生成 profile 就用 `,id=195476,gem_id=240983,ilevel={}`（sc_evoker.cpp），
`decode_ilevel` 只在超范围时才 throw。所以 `head=,id=268230,ilevel=334,enchant_id=7961` 没问题。

### 改法
1. `_simc_line`：名字一律留空（`parts = [""]`），只写 id
2. checksum：一件没动 → 原样还回去（导出仍逐字节等于原文）；改过任何东西 → **整行去掉**。
   理由写进注释：它是"原样输出"的凭证，改完再带就是假凭证，重算同属冒充且无从自证。
3. serve `/api/export-simc` 新增 `checksum` 字段，前端据此说明
4. 前端弹层写明：**别用 Top Gear / Stat Weights 的「SimC Addon」输入框**，那个框只认插件原样，改过一律拒；正确入口是 Quick Sim
5. 测试更新「导出校验和」语义 + 新增「导出行不写名字」

### 关键认知
- Raidbots 有三个入口，语义不同：Top Gear 的 SimC Addon 框 = "导入真实角色"（严格），
  Quick Sim = "任意合法 profile"（宽松）。我们这种"改了装备的 profile"只能走后者。
- 这是"想当然比错误更危险"的例子：补英文名看起来是改善，实际让整份 profile 失效。

### 用户实测结果（比预想的好）
修复后 Top Gear 直接接受，只是左下角多一个红色 **`Edited`** 角标，
悬停提示 "Addon input has been edited. Raidbots tools are not guaranteed to work as expected."
角色卡片、装备图标、方案名 anni、装等 335 全部正常渲染。

**说明 Raidbots 就是靠 `# Checksum` 判断"输入有没有被改过"**：
- 有 checksum 且对得上 → 正常
- 没有 / 对不上 → 标 Edited，但**照收**
所以"去掉 checksum"这个决定是对的，它换来了一个诚实的标识。
**之前说"只能 Quick Sim"是错的**：Quick Sim / Top Gear / Stat Weights / Advanced 全都能用。

### 为 Top Gear 补的兼容
`### Gear from Bags` 整段是全注释（插件不写真正的装备行），但它是 Raidbots 的
**可选装备池**——Top Gear 的勾选框从这里枚举。所以换装后必须把两件都补进去：
- 换上的那件（游戏里不存在）
- 原来那件（被换掉了，不在身上）
不补的话两头都看不见，"原 vs 新"比不了。原件的 `bonus_id` 能从原文解析出来完整保留，
新件只有 `ilevel`。

### 遗留
- 换过的装备没有 `bonus_id`，只写 `ilevel` → simc 按装等重算属性，
  套装转化件/制造业可能与游戏有细微差别（原文有的部位是原样搬运，不受影响）
- 背包注释里补的新件同样缺 bonus_id，Top Gear 把它当"同装等的另一件"处理，
  属性可能和游戏里那件略有出入

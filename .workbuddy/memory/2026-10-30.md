## 装绑 vs 制造业：属性机制搞清楚了

用户补充：装绑 = 团本小怪掉落的随机属性神话装备，没有固定 id，拍卖行上按装等认。

| craft_kind | 来源 | 槽位 | 分配 |
|---|---|---|---|
| crafted | 制造业 | 24+25 或只有 24 | 双槽平分 3500:3500；单槽 7000 全占 |

（`8793: [49,36]` = 精通占大槽、急速占小槽）。

```
python src/stat_picker.py list --kind boe
```

### 两个必须记住的坑

1. **grid 会把行压扁**。原来 `.cands` 用 `display:grid`，内容超过容器高度时 Chrome 把行
   压到 min-content，卡片的属性行和差异行直接叠在一起。`align-content:start` 和
   `grid-auto-rows:max-content` 都救不了。换 `display:flex; flex-wrap:wrap` 才正常。
   另外卡片是纵向 flex，得给子项 `.card > *{flex-shrink:0}`，否则内容多了照样被压缩。

2. **innerHTML 会连 id 一起冲掉**。装等按钮里 `<b id="ilvl-val">` 是子元素，我既单独
   `$("ilvl-val").textContent = x` 又整块重写 `$("ilvl-btn").innerHTML`，第二次调用
   拿到 null 直接抛 TypeError，表现是"点装等没反应、面板还开着"。以后整块重写时
   把 id 写回模板里，不要再单独取那个节点。

3. 端口上可能同时挂两个 serve 进程（`allow_reuse_address` 让它们都能绑上），
   请求随机落到旧进程，改了代码不生效。改完代码先 `netstat | grep 8765` 确认只有一个，
   有多个就全杀掉再起。

## 第四轮：套装绿字、面板基准、百分比、图标（用户四条反馈）

### 套装转化件的绿字（最重要）

`item_stats` 里给 catalyst 件存的那套属性**只是模板**，实际转化出来继承被转的那件。
simc 用 `redirected_base_stats` 记源装备。

猎人头亲眼对比：模板 急速 4993/精通 2007，源装备（Sethraliss' Fanged Helm 239035）
实际 暴击 2750/精通 4250。差了整整一个属性。

修法：`item_payload(..., stat_src)` 从源装备查 stats，snapshot 传
`item.extra.get("redirected_base_stats")`。候选里的 catalyst 件不给数值，
只写"属性继承转化前的装备"+套装名（还不知道你要拿哪件去转）。

顺带一个前端坑：候选列表渲染时 `isCur` 为真也要用 **snapshot 那份**（带 stat_from），
用 candidates 那份就还是模板值。

### 面板基准

simc 字符串里**没有**面板属性（只有装备 id + bonus_id，`### Additional Character Info`
里只有纹章和 `slot_high_watermarks` 装等）。所以让用户填一次：顶栏「面板校准」，
6 个输入框存 `data/panel.json`。

`base = 面板 − 首次装备合计`，之后 `显示 = base + 装备`。NaN 风险在 base 为负：
装备算多了（精通 1491 vs 面板 1423）要保留负 base，否则填什么显示就不对。

实测对上了：敏捷 2861 = base 1096 + 装备 1765；耐力 42612 = base 39884 + 装备 2728
（耐力基础值占 94%，难怪之前只算装备时数字离谱）。

### 百分比

`RATING_PER_PCT` 从真实面板反推（用面板里的 4 组 rating/pct 值算）：
暴击 27.92、急速 25.16、精通 17.90、全能 53.97。网上传的"46=1%"是旧版本，会差一半。
只在战斗等级上算百分比，主属性/耐力没有。没做 1320+ 的递减修正，高评级会略偏高。

### 图标

加了 86 件复刻装备后，它们的 Zandalar/KT 老图标没下载过，`data/icons` 只有 441 个，

直接就给了），最后 1 个是数据源把名字写成 `inv__misc_herb_marrowroot_leaf`（双下划线，
icon-index.csv 里其实是 `inv_ misc_...` 带空格），用 CASC 按 fdID 3480676 单独补的。
现在 513/513 全覆盖。

教训：加内容（新副本/新赛季）之后必须重跑图标，`fetch_icons.py` 是按 items 表现有图标算的，
不会自动跟进——要主动看一眼"需要 N 个 / 有 M 个"。

## 第五轮：左侧格子副属性 + 制造业绿字丢失

用户反馈：左侧格子要显示副属性；左侧制造业那两件没显示具体属性，装绑大概同样有问题。

### 根因：自选槽的占位 code 没被替换

制造业/装绑的自选槽在 `item_stats` 里只有 `stat_id=24/25`，join 出来 code 是
`bonus1`/`bonus2`。`stat_values()` 已经按 `crafted_stats` 把它们算成 `vers`/`mastery` 了，
但 `item_payload` 返回的 `stats` 里 code 还是 `bonus1` —— 前端拿 code 去 `stat_values` 里查，
查不到就没行可渲染，整件装备看起来只有耐力+敏捷、一条绿字都没有。

修法：`item_payload` 在收敛多形态主属性之后，再遍历 optional 槽，按 `crafted_stats`
把 code/label 换成真实属性。顺序必须和 `stat_values` 的 idx 计数一致（都只数 optional）。

装绑同理，只是角色身上没穿装绑，左侧看不出来；候选里之前只显示"待指定"，也没暴露。

### 候选里的自选槽要写点数

新增 `optional_each`（每个自选槽能提供多少点，按当前装等算）。卡片上「自选槽 122 × 2」，
差异行末尾补「+ 自选绿字 244」。只写"待指定"等于没给信息，用户没法比较。

槽位比例是真实的：制造业 7000 拆 3500+3500 或整块 7000（单槽），装绑 65:35 左右。
同装等两件制造业头一个是 `251 × 1`、一个是 `125 × 2`，总量都是 7000 —— 不是 bug。

### 左侧格子副属性

`eqCell` 加第三行 `secLine()`：只列绿字，降序留两条，多的 `+N`，title 挂全量。
无绿字的饰品写「无绿字」。主属性不放——顶部有总数，单件那点数字判断不了什么。

## 第六轮：属性公式推倒重来 + 项目模块化

用户说"副属性会随装等变化，你没做这一环节"，并开了代理（127.0.0.1:7897）让我重试 wowhead，

### 属性公式终于对了（重要）

**wowhead 有 tooltip API，不需要爬页面**（页面被 CloudFront 403）：
`https://nether.wowhead.com/tooltip/item/<id>?dataEnv=1&locale=0&ilvl=<装等>`
只改装等参数就能拿到该装等的真实属性。走代理 `curl -x http://127.0.0.1:7897`。

**三个发现，全都推翻了旧实现：**

1. **主属性 / 耐力 / 绿字是三条不同的曲线**。`RandPropPoints` 只能算主属性
   （331 装等档位1 = 196.13，实测护腕敏捷 K=195.9 ✓）。绿字在表里任何一档都不是，
   是独立的近线性曲线。耐力是主属性的 13~14 倍。用旧公式算绿字 331 装等**高估 22%**、
   低装等反而偏低。

2. **部位只有两档，不是三档**。331 装等实测：头部敏捷 138、脚部敏捷也是 138，
   绿字都是 149。旧代码把头胸腿放档位 0（348.68）、肩手腰脚放档位 1（261.51），
   导致头胸腿凭空高三成。

3. **耐力之前少算 13 倍**（155 vs 实际 2124）。修正后角色装备耐力 31957，
   base 从 39884 降到 10655，所有 base 都变正数了——这是公式正确的旁证
   （之前精通 base 是负的，说明装备算得比面板还多，显然不对）。

实现：`data/stat_curve.csv` 25 个采样点（250-346 每 4 级），三类部位 × 三个系数。
`tools/sample_curve.py` 负责重新采样（换赛季要换装备 id）。
验证：护腕 331 算出 103/2125/56+56，wowhead 是 103/2124/56+56，误差 <1%。

### 截图里那两个"重复"是怎么来的

用户截图里主手格多了一行绿字、副手空格里出现"无绿字"。先说结论：**代码里没有这两行**。

**真正需要修的 UI 问题**是另一个：装备名会顶出格子右边框
（`Greaves of the Noxious Depth` 直接压在隔壁格子上）。根因是 grid 列 `1fr` 的

### 平均装等（用户让"公式自己找"）

游戏角色面板的口径 = **16 个格子装等之和 ÷ 16**：
- 空格算 0
- **双手武器算两次**（同时占主手和副手）。不这么算，猎人拿弓会平白低 20 多装等
- 单手 + 空副手，副手就是 0，不能补

双手判定用 `items.inventory_type`：15（弓/枪）、17（双手武器）、26（远程右手）。
样例角色算出 332.94（武器 341 计两次），15 件装备 16 格，和常识吻合。

悬停候选卡时这个数字也跟着变（`preview_full` 同时返回 totals 和 avg）。

### 账号体系

`src/wowgear/accounts.py` + `data/accounts.db`（**独立于 wowgear.db**，
游戏库随赛季重建，账号重建一次就全没了）。

四张表：users / sessions / simc_history / loadouts。
密码 `pbkdf2_hmac('sha256', ..., 120000)` + 16 字节 salt，登录失败时"用户不存在"和
"密码错误"返回同一句话（否则就是用户名探测器）。

**会话改成按令牌分开**：`STATE = {"anon": None}`，key 是 `u<id>` 或 `anon`。
以前单一全局 `STATE["session"]`，一支持账号就会出现"A 登录着，B 打开把 A 顶掉"。
两个体验细节：登录时把 anon 那套装备过继给账号；退出登录只挪回 anon 位，不销毁。

**存档存「原文 + 改动」而不是最终数值**：属性公式一改，存死的数值就永远停在保存那天；
存原文+改动，载入时重算。代价是依赖装备 id，赛季换库会丢几件，
所以 `apply_changes()` 跳过认不出的而不是整份失败。

接口：/api/register /api/login /api/logout /api/me /api/history/{load,delete}
/api/loadout/{save,load,delete}。越权条件写在 SQL 的 WHERE 里。

## 第九轮：入口页 + 视觉重做

### 为什么必须有入口页

原来打开就是主界面，没角色直接弹导入框——第一眼看到的是上次残留的样例装备，
像是"这工具在用我的数据"。现在整页入口：登录 / 注册 / 游客。

`boot()` 里的判断顺序：有登录 cookie → 进主界面；`sessionStorage.wg.guest` → 进；
都没有才停在入口页。游客标记用 sessionStorage 不用 localStorage，关标签页就该忘掉，
否则第一次点了游客，往后永远看不到注册入口。

游客第一次进主界面**不读**服务端残留的 anon 会话（`wg.entered` 控制），
否则一开门就看见一身不认识装备。

### 底图怎么拿的

`blizzard.gamespress.com/zh-TW/wowmidnightlaunch` 页面里图片的真实地址带 SAS 签名，
藏在 HTML 的 `data-preview` 属性里，`html.unescape()` 之后 curl 就能下。
**直链去掉 `?sv=...` 会 404**，签名约 3 小时失效。
选 "Stand As One" key art：人物中偏左、右侧翻滚着虚空紫，正好右下放登录卡。
存 `src/web/img/stand.png`（3.7MB）。`.gitignore` 的 `*.png` 要单独开例外，
否则这张图进不了库。

### 反"AI 味"的几条（都是具体判断，不是形容词）

- **配色分工**：底 `#08060d`，面板 `#120c1a`，金 `#d4b478` 只做骨架（线/框/标题），
  青 `#6ec9d8` 只做交互（选中/悬停）。金是静的骨架，青是动的手，两个强调色别混用
- **圆角收到 3~5px**。满屏 8px 圆角是模板感最重的来源
- **标题用宋体**（`Songti SC/STSong/SimSun` 链）且 `font-weight:400`：
  SimSun 的合成粗体在 54px 下笔画糊成一团，靠多层 `text-shadow` 撑分量反而更挺
- **输入框只留下划线** + 一道极淡的金色渐隐底。纯下划线在近黑底上等于不存在，
  密码那格会看起来像块空白（这是实测出来的）
- **登录/注册用下划线指示**，不用药丸标签——少一层填充色，块面才干净
- **构图底部对齐**：标题贴左下、卡片贴右下，上半整块留给美术图。
  垂直居中会把画面切成两半，key art 就白放了
- **品质色**：`.eq[data-q]` 描边、`.card[data-q]` 用 `inset 3px 0 0` 做左侧色条。
  用 `border-left` 会把卡片撑宽 2px，两列立刻错位

### 三个踩到的坑

1. `.ld-hero` 在单列（<1080px）模式下 `align-self:stretch` + `justify-content:flex-end`
   会把标题顶到紧贴卡片上沿，媒体查询里必须改回 `align-self:start`
2. 空属性栏只清 `innerHTML` 不收 `display`，`min-height:64px` 还在，
   顶上留一条空横带，看着像渲染失败
3. logout 后清空 state 却留在主界面，人分不清自己是登录态还是游客态 → 回入口页

Edge headless `--screenshot` + 同源 iframe 打点（`_selftest.html` 点按钮、把中间结果
打到页面底部绿色小字一起截图），测完删。**`--user-data-dir` 必须每次换**，
否则 sessionStorage / cookie 复用，测出来的是上一轮的状态。
虚拟时间预算（`--virtual-time-budget`）不够时脚本会在某个 await 上截断，

## 第十轮：CSS 类名撞车 + 目录重组

### 用户报的"黑框"

截图放大后才看清：每个装备格子里，"部位 + 装等"那行有一块独立的深色矩形，
右边缘还多一条竖线，超出格子边框。用户判断"你应该是分成两部分写弄了一个叠加"。

实际原因是**类名撞车**：顶栏 `.top` 和装备格里那行 `<div class="top">` 同名。
`.top{height:50px; background:var(--panel); border-bottom:1px solid; position:relative}`
全部漏到了格子里——`padding:0 16px` 让那行比 body2 窄，`border-bottom` 就是那条竖线/横线来源，
我后来给顶栏加的 `.top::after` 金线也一起漏进去了。

定位方法：写个同源 iframe 探针页，遍历 `.eq` 的所有后代，打印
`tag.class / getBoundingClientRect / computedStyle.backgroundColor / borderWidth / boxShadow`。
一眼看到 `div.top bg=rgb(0,12,28)` —— 这行本来不该有背景色。

修法：顶栏改名 `.topbar`，CSS 里 7 处选择器跟着改。
**教训：`.top` `.left` `.right` `.bar` `.body` 这种泛词当类名，早晚撞。
要么加命名空间（`.app-top`），要么直接叫得具体点。**

### 目录重组（用户要求"按模块创建文件夹"）

原来是 `src/` 下 12 个 .py 平铺 + 一个 wowgear 包，构建脚本和运行时代码混在一起。

现在四层：

    src/wowgear/   核心：paths const curve stats source store accounts（不 import 上层）
    src/wowlib/    业务：simc calibrate stat_picker catalog session
    src/server/    serve.py
    src/build/     建库/图标/套装反查/加装备（离线跑，不进运行时）
    src/web/       index.html + css/ + js/ + img/

关键判断：
- **`catalog.py` 从 wowgear 挪到了 wowlib**。它要判断职业能不能穿，得用 simc 的
  `class_primary`，留在核心层就是数据层反向依赖解析层。挪出去以后 wowgear 才是真的纯。
- **`wowconst.py` 删掉了**。它自己的注释写着"新代码请直接 from wowgear.const import"，
  留着的唯一理由是不想一次改十几个 import —— 既然要动就一次改干净。
- **路径统一到 `wowgear/paths.py`**。挪目录时暴露了 5 个文件各自用

    css/ base(变量/reset) landing(入口页) app(主界面) account(抽屉/表单/响应式)

## 第十一轮：会话归属、simc 导出、体积体检

### "登录了还看到样例"是怎么回事

两个错叠在一起：

1. `STATE` 里未登录只有一份 `"anon"`，**所有浏览器共用**。A 粘的装备，B 打开就看到。
2. `_issue()`（登录发令牌）里 `anon = STATE.pop("anon")` 然后无条件塞进 `u<uid>`。
   于是"别人的 anon"或"自己昨天试的样例"被过继进账号，登录后第一眼看到的
   不是自己的角色。

修法：给未登录浏览器发 `wg_aid` cookie（一年），会话键用 `a<浏览器id>`；
登录**不继承**；退出只失效令牌，两边会话都不动（账号的留着重登能接上）。

教训：**"防止用户丢工作"的自动化，一旦作用在共享状态上就会变成"数据串味"**。
过继本身没错，错在 anon 不是 per-browser 的。

### 导出 simc 给 Raidbots

`Session.to_simc()`：**逐行重写 raw_text，只替换换过的部位**。

不能从零拼，会丢三类字段：
- `redirected_base_stats`（套装转化件的源装备，丢了属性按模板算，全错）
- `content_tuning`
- `crafting_quality`（制造业品质档位）

换过的部位用 `名字,id=X,ilevel=Y`，并**沿用原槽位的 gem_id / enchant_id**——
属性计算用不到宝石附魔，但 Raidbots 会算，不带的话模拟少一截
（戒指项链尤其明显）。`_make_item()` 里继承 old 的 gem_ids/enchant_id。

接口 `/api/export-simc`，前端顶栏「导出 simc」→ 弹层（textarea + 复制 + Raidbots 链接）。

### 体积

- 底图 3.7MB PNG → **388KB JPEG**。机器上没有 PIL / ffmpeg / magick，用 Edge headless
  打开一个 canvas 转码页，`--dump-dom` 把 `toDataURL('image/jpeg',0.85)` 的
  base64 打到 DOM 里，python 正则抠出来解码。以后要压图可以复用这招。
  （系统自带的 System.Drawing 方案被安全策略拦了，不让运行时编译 .NET。）
- `data/raw` 56MB 是最大头，但它是建库原料，删了下次 --build 要重下。
- 新增 `python main.py --size` 列出各处占用并标注哪些能删。
- 服务进程 42MB 工作集 / 24MB 私有，正常。

### 顺带清掉的重复

`session.py` 里自己抄了一份 `STAT_CN / SHOW_ORDER / KIND_CN / QUALITY_CN / TRACK_CN`，
和 `wowgear/const.py` 一字不差；`calibrate.py` 抄了 `stats.py` 的 `STAT_ID`。
全删，改成 import（`STAT_ORDER as SHOW_ORDER`）。

### main.py --web 的坑

原来用 `subprocess.call` 起 serve.py，父进程退出后子进程还活着占着 8765，
下次启动直接 Address already in use，而且不知道杀哪个 PID。
试过 `os.execv` 替换进程，但后台任务管理器会把进程当"已完成"清理掉。
最终：保留 subprocess + 启动前用 `socket.connect_ex` 探测端口，占了就给一句
人话提示。

### 测试脚本为什么老卡

`--virtual-time-budget` 超过 10s 时 headless 容易挂死，命令 SIGTERM、没有截图。
压到 8500ms 一次就过。

## 第十二轮：宝石与附魔进计算

### 为什么这块一直没做

`gem_id` / `enchant_id` 从第一版就解析出来了，存在 EquippedItem 里，导出 simc 也带着，
但 `calibrate.compute` 从来没用过——数据"都在"，就是一分属性没加。

这是最典型的"看着有其实没有"。样例角色光四颗宝石就差 21 点精通，
用户说的"1403 vs 1423 差 20"就是这个。补上之后 gear_totals 精通 = 1424，面板 1423，差 1（取整）。

### 数据源：绕了三圈才找对

按顺序试过这些路，前四条都不通：

1. **wowhead 网页（`www.wowhead.com/item-enchantment=7961`）**：403。CloudFront 反爬，
   加 UA 也不行；`nether.wowhead.com` 的 tooltip 接口才是能用的那条（免反爬，但要代理）。
2. **`nether.wowhead.com/tooltip/spell/<id>`**：给名字，不给数值
   （"Eyes of the Eagle" 就一个名字）。因为附魔数值不在 spell 描述里。
3. **wago.tools 的 `SpellItemEnchantment` CSV**：结构完整，但 `EffectPointsMin` 全是 0，
   只有 `EffectScalingPoints` 和 `ScalingClass=-7`。要自己推缩放曲线，风险大。
4. **`SpellEffect` 表反查光环**：戒指附魔的 EffectArg 指向的 spell 效果是
   `EffectAura=163, EffectBasePointsF=2`，解释不出来。

**最后通了的路：附魔卷轴物品的说明文字。**

```
permanent-enchant.inc   enchant_id → enchant_boots__lynxs_dexterity
ItemSparse              名字 → 卷轴 item id（580 品质那档）
wowhead item tooltip    卷轴 id → "increasing Avoidance by 15 and Stamina by 186"
```

`permanent_enchant.inc` 在 `simulationcraft/simc` 仓库的 `engine/dbc/generated/` 下，
86KB，1062 条，正好是 build 12.1.5.70575。raw.githubusercontent 直连可用（不用 ghfast）。

### 三个必须记住的坑

1. **名字要归一化再比。** inc 里是 `lynxs_dexterity`（撇号被吃掉）、`farstriders_hunt`；
   卷轴上是 `Lynx's Dexterity`、`Farstrider's Hunt`（多个 s）。直接比只匹配上 21/44，
   压成 `lynxsdexterity` 之后 38/44（剩 6 条是采集工具附魔，与装备无关）。
2. **`+ 1 Critical Strike` 加号后有空格。** 老宝石的 tooltip 渲染成 `+ 1`，
   正则写 `\+(\d+)` 会把它们全判成"认不出"。要 `\+\s*(\d+)`。
3. **宝石不能用装等筛。** 老宝石（BfA 那批）ItemLevel 是 385，新宝石 295，
   用 `>= 290` 会新的一颗不留、旧的抓一堆。判据是 `ExpansionID == 11`。

### 为什么取 580 品质的卷轴

DBC 里同一附魔有 rank1 / rank2 两个 id，名字带 `Tier2` 图标。
实测 7961(rank2) 系数 × 26.9 = 44，正是 580 卷轴的值；595 卷轴是 55。
**Tier3 在 DBC 里没有独立 id**，所以 SimC / Raidbots 也只能用 Tier2。
跟着它取 580，"本地算"和"导出去 Raidbots 跑"两边才对得上。

顺带验证了三桶曲线：主属性/耐力档 S≈26.9，绿字档 S≈30.8。和 curve.py 的设计吻合。

### 附魔这一版基本不给主副属性

38 条里只有 8 条给主属性/绿字（胸 +32 敏捷/力量/智力、戒指 +22~27 暴击/急速/精通/全能），
其余全是第三属性（吸血 22~132、闪避 15~89、移速 9~52）或百分比特效。

**`critical strike effectiveness by 1%` 绝不能当 `crit +1`。** 正则里 "critical strike"
能被匹配两次，偷懒的话戒指附魔会让暴击凭空多 1 点，看着像没问题其实整条错。
解析时带 `%` 的一律进 `note` 字段，只展示不参与计算。

### 界面

- 装备格"部位+装等"那行加两个字符标记：`◆` 有宝石（青）、`✦` 有附魔（金）。
  不用图标是因为格子只有 72px 高，塞图会把名字挤掉一行。
- 悬停提示里宝石/附魔各占一行，和绿字用不同颜色分开（它们不随装备装等变）。
- 属性按固定顺序排（agi/str/int/sta/crit/haste/mastery/vers），
  按 JSON 键序会出现"暴击 +16 精通 +7 敏捷 +32"，主属性跑最后像算错了。
- **查不到的附魔显示"未收录，不计入"**，不静默算 0。腿部 `8159` 就是这种情况
  （不在 SimC 的 44 条清单里），静默跳过的话用户只会觉得面板莫名其妙少一截。

### 数据落库

`gems` / `enchants` 两张表，属性存 JSON（一件宝石可能同时给两项）。
原料 `data/raw/gems.json`（75 颗）+ `enchants.json`（38 条），
由 `src/build/fetch_gems_enchants.py` 生成，`build_db.py` 读它们建表。

中间用的 `.item-sparse.csv`（50MB）和 `spell-item-enchantment.csv` 用完删了，
否则 data/raw 从 57MB 涨到 107MB。重新抓的话脚本里写了下载地址。

### 抓取脚本的两个环境坑

- **urllib 在 Windows 不认 `HTTPS_PROXY`**，必须显式 `ProxyHandler`。
- 有些环境（编辑器沙箱）会往 `HTTP_PROXY` 塞自己的内部代理（实测 56250），
  照它走反而连不上。所以加了 `--proxy` 参数和 `WG_PROXY` 变量，优先级高于标准环境变量。

### 还没解决的

  （904 vs 1065）、敏捷差 1184、耐力差 6971。这些差额现在压在 `base` 里，

- `panel.json` 必须和导出文件是同一身装备。换了装不改面板，差额全压到 base，

## 第十三轮：宝石与附魔自选

### 做法

右侧面板加「装备 / 宝石 / 附魔」三种模式，共用同一个选中的部位。
`state.mode` 一个字段控制，`renderCands()` 开头分发到 `customize.js` 的两个渲染函数。

- 宝石：顶部孔位条（最多 3 个）+ 下方 75 颗宝石列表。先点孔再点宝石。
- 附魔：按 `db_slot` 过滤，点一下直接换，当前那条高亮。
- 两者都走 `/api/gem` `/api/enchant`，成功后返回整份 snapshot 让前端重画。

**没有做孔数校验**：数据库里只有 45 件装备带 `socket_info`，其余只知 `has_sockets=1`，
按它卡会误伤一大片。允许插 0~3 颗，靠玩家自己把握，README 里写了。

### 撤销复用了换装的栈

`history` 存的是整个 `EquippedItem`，所以 `_mutate(slot, old, **changes)` 用
`dataclasses.replace` 造一个新的塞进去，改宝石/附魔天然可撤销。
**不要另造一个栈**：两个栈的 pop 顺序一定会打架（先换装再换宝石，撤销先撤哪个？）。

`_mutate` 里 `if new == old: return False`——值没变就别记，否则连点两下要撤两次。

### 坑一：导出 simc 丢宝石（最严重）

改完宝石后导出，neck 那行还是旧宝石。原因：`to_simc()` 里 `if self._changed(k)`
只看 `item_id`，判定"这件没换过"，于是原样搬了**原文那一行**。

但这里不能简单地"改成 `_changed` 也比较 gem_ids" —— 一旦走 `_simc_line()` 整行重写，
`redirected_base_stats` / `content_tuning` / `crafting_quality` 就全丢了
（套装转化件丢了源装备 id，属性按模板算，全错）。

正确做法是**第三种情况**：

```python
if self._changed(k):        out.append(self._simc_line(k, item))    # 本体换了，整行重写
elif self._customized(k):   out.append(self._patch_line(line, item)) # 只换 gem_id/enchant_id 段
else:                       out.append(line)                        # 一字不动
```

`_patch_line()` 摘掉原行的 `gem_id=` / `enchant_id=`，按需追加回去，其它字段原样保留。
实测 head 行改完仍带着 `redirected_base_stats=239035` 和 `enchant_id=7961`。

### 坑二：正则里的 `and` 太宽泛

附魔要支持两项 `increasing Avoidance by 15 and Stamina by 186`，
所以写成了 `(?:increasing|and)\s+(.+?)\s+by\s+(\d+)`。

结果武器附魔全崩："...and abilities to sometimes grant you Precision of the
Dragonhawk, increasing Critical Strike by 99%" —— 从那个 `and` 一路吞到句尾，
note 变成一句没头没尾的英文。

修法：捕获组限制成 `([A-Za-z][A-Za-z /]*?)`，跨不过 ", increasing" 这一刀。
另外 `text` 截断从 200 改到 400——200 会把武器附魔的说明截半，note 直接空。

**这一改不需要重抓**：`enchants.json` 里存了 `text` 和 `item_id`，重新 parse 即可。
只有确实被截断的那几条才需要按 item_id 单独补抓。

### 坑三：`const state` 不挂 window

写点击测试时用 `iframe.contentWindow.state` 拿不到，因为 `const` 是脚本作用域，
不挂全局。要 `contentWindow.eval("state")` 才读得到。

（这也解释了为什么页面上其它代码能用 `state`——它们在同一个脚本作用域里。）

### 界面判断

- 模式按钮做成三个小按钮而不是大 tab：切的是"看这个部位的什么"，不是并列内容区
- 宝石用属性配色（暴击红/急速黄/精通紫/全能蓝/主属性橙），不用图标：
  75 颗宝石一张图标都没下过，硬要显示就是 75 个空框
- 宝石卡用 `min-width:240px` 而不是只写 `flex-basis`：只写 basis 的话
  flex-shrink 会把它压到 170px，名字全变成 "Indecipherable Everso..."
- 宝石/附魔模式要 `$("tabs").innerHTML = ""`，否则"全部/副本/M+/制造业"那排
  装备来源筛选还挂在那儿
- 附魔特效文案要在后端翻成中文（`_note_cn`），不然中文界面里冒一行英文

### 验证

- 119 项测试全过（新增 17 项：换/拔/追加/撤销宝石、换/移除/跨部位附魔、导出跟随）

## 第十五轮：宝石与附魔自选完善（中文名 / 预览 / 孔位）

### 起因：三处具体的"用不下去"

### 中文名：只能走 ItemSparse，wowhead 这条路对宝石是死的

  （wago.tools 直接给 CSV，48MB，`fetch_names.py` 抽完自动删）。
- 顺带发现客户端的中文命名和字面直译差很远：Peridot=榄石（不是橄榄石）、
  Amethyst=紫晶、Garnet=榴石、Diamond=永歌钻石、Heliotrope=鸡血石、
  精良档是"无瑕"（不是"完美"）。`build_db.GEM_FAMILY` 原来那套译名游戏里没人这么说，
  已改。
- 只抽用得到的 id：装备取 `equippable-items.json` 里有属性的（build_db 只入库这些），
  宝石取 `gems.json`、附魔取 `enchants.json` 的卷轴 id。全表 17.5 万行存下来要十几 MB，
  没必要；现在 `names_zhcn.json` 3.3MB。

### 同名宝石的悬案：是同一颗宝石的两个装等

75 颗里有 12 对"名字、品质、图标完全一样、数值差 1~2 点"，一直分不清。
ItemSparse 里一眼看穿：**同一颗宝石有两个装等版本（278 / 295）**。
库里 `gems` 加 `ilvl` 列，卡片上写出来，两张卡才分得清；孔位条也带这个数字。

### 预览：复用装备那套 state.hover，服务端算

`preview_gem` / `preview_enchant` 在 Session 里临时替换、`compute`、再放回，
接口 `/api/preview-gem`、`/api/preview-enchant` 返回 totals + delta。
前端 `hoverCustomize()` 把结果塞进 `state.hover`（多一个 `label` 字段），
属性条那段代码一行没改。悬停已插的孔预览的是"拔掉少多少"。

**预览绝不能落地**：这是"鼠标划一圈就改掉配装"的经典事故，测试专门盯了这条。

### 孔位是位置，不是数量

`gem_ids` 改成按孔位对齐、空孔用 0 占位（末尾的 0 裁掉）。
SimC 自己就是这么导的（`ref/item.cpp` 里 `range::fill(gem_id, 0)` 之后照样写 0），
所以 `gem_id=0/240983` 是合法写法。同步改了三处：
- `session._gems_after()`：拔/插都按位置，pop 改赋值 0
- `calibrate.gem_values()`：0 不是宝石，不查库、不报"认不出"
- `simc._trim_gems()`：**解析时保留开头的 0**。原来 `gem_id=0/240983` 被丢成
  `(240983,)`，第 2 孔的宝石被读成第 1 孔，位置整个前移。

### 顺手修掉的一个存档丢数据

`changes()` 只比 item_id/装等/自选属性，**改了宝石附魔不算改动**——存完配装再载入，
宝石悄悄回到导入时那几颗。现在改动里带 `gems` / `enchant`，`apply_changes()` 恢复，
老存档没有这两个键就保持原样。

### 界面上的小改

- 宝石卡：中文名（去掉"无瑕"前缀，品质单独标）+ 品质 + 装等 + "本孔"标记
- 孔位条：每颗带装等，hint 里给"已插 N 颗（合计 急速 +16 全能 +7）"
- 附魔卡：中文名 + "当前"标记；点完有 toast（"已附上 阿曼尼精通"）+ 属性条挂 2.6 秒增减
- 附魔空部位：分清"这件装备上的附魔没收录"（腿部 8159）和"这个部位没有附魔"，
  并列出本赛季收录了哪几个部位各几条

### 验证

- 测试 127 → **150**（新增：解析保留空孔、拔中间孔不移位、空孔导出成 0、
  预览不落地、宝石带装等与中文名、附魔覆盖部位、存档带回宝石附魔）
- headless 截图逐项核对：宝石悬停预览（暴击 -16 / 急速 +16 / 精通 -7 / 全能 +7）、

- 冒烟：登录态 → 导入 → 换装 → 换宝石 → 换附魔 → 撤销 → 导出 simc，字段都跟着走

## 第十六轮：打孔器自选开槽（头 / 腰 / 腕）

用户要求：头、护腕、腰带在游戏里能用打孔器开一个槽，做成自选开槽。

### 先确认边界：SimC 根本表达不了"额外插槽"

- 最新 SimC 的 `engine/item/item.cpp` 里 item 选项一共 36 个，**没有 `sockets=`**；
  只有 `gem_id` / `gem_bonus_id` / `gem_ilevel`。孔的多少来自它自己的物品数据
  （`parsed.data.socket_color`），不是 profile 给的。
- 所以 `sockets=1` 这种写法导出去 Raidbots 那边是不认识的字——严重时会解析失败。
- 结论：**本地能规划，导出必须明说**。不写 `sockets=`，导出弹层点名哪几件用了打孔器。

### 做法

- `EquippedItem.drilled: int`（0/1），跟着撤销栈走（history 存整个 item）。
- `DRILLABLE_SLOTS = {head, waist, wrist}`，`can_drill()` 只在这三个部位且没开过时为真。
- `socket_count(..., drilled)`：孔数 = `max(库值, simc sockets=, 宝石证据) + drilled`。
  **宝石证据要减掉 drilled**：开完孔插上宝石，`len(gems)` 会比真实孔数多 1，
  不减的话下一轮又把它算成"本来就有这个孔"，再开一次就变两个孔（实测会翻倍）。
- 撤孔时如果那个孔里还插着宝石，直接拒绝并说清楚——不然宝石会凭空消失。
- `changes()` / `apply_changes()` 带上 `drilled`，存档能还原开孔状态。
- 换装备时 drilled 不继承：新装备是另一件，没开过孔（宝石才跟着槽位走）。

### 界面

- 宝石面板在孔位条下面给一行虚线按钮「＋ 用打孔器开一个孔 头/腰带/护腕，每件限一个」。
- 没孔的头/腰/腕不再直接说"插不了"，而是给这个按钮 + "先用上面的打孔器开一个"。
- 开过之后按钮变金色实线「打孔器 · 已开 1 个孔 · 点这里取消」——金是"已经花掉的材料"，
  不能看起来像还能再开。
- 导出弹层加一条金色提示（不是红色，这不是错误）：哪几件用了打孔器、Raidbots 会少算这点属性。

### 验证

- 测试 150 → **163**：孔数只加一次、开出来的孔能插宝石且属性跟着涨、有宝石不能撤孔、
  撤孔归零、只有头腰腕能开、额外孔不写进 simc。
- 实操：head 0 孔 → 开 → 1 孔 → 插宝石 精通 +7 → 再开一次不变 → 撤孔被拦 → 拔宝石后撤掉；
  导出弹层正确列出"头部"。
- 截图核对了开孔前、开孔后、导出提示三个状态。

### 教训

- **功能能不能做，先看格式支不支持**。如果先写 UI 再发现 simc 表达不了，
  要么白做，要么做出"本地和 Raidbots 数字不一致"的坑。
- 计数型的推导字段（孔数、属性合计）一旦混进"证据"（插了几颗宝石），
  加一个派生量就必须把证据里的那份减掉，否则每轮都会自我放大。

## 第十七轮：附魔数据修整（腿部护甲片 / 触发特效 / 主属性）

用户截图指出"附魔不正确，腿部还有装甲片什么的"。查下来是**四类错**叠在一起。

### 一、腿部一条都没有：过滤条件吃掉了 92% 的表

`permanent-enchant.inc` 有 1062 条，脚本用 `if not name.startswith("enchant_")` 过滤，
剩下 88 条——而护甲片/魔线在 inc 里叫 `forest_hunters_armor_kit`、
`arcanoweave_spellthread`，**不带 enchant_ 前缀**，全被丢掉。
它们对应的物品也不叫 "Enchant XXX - YYY"，按 "Enchant " 前缀对卷轴当然一条都找不到。

补了 6 条腿部（3 护甲片 + 3 魔线）。数值来源：客户端
`SpellItemEnchantment.ench_coeff`（SimC 生成的 `spell_item_enchantment.inc`）
× 580 档基数 26.99，例：8159 系数 3.4194/1.2191 → 敏捷 92 / 耐力 33。
**这 6 条没有 wowhead 原文可对**，已在 README/卡片提示里标明"按系数推算"。

### 二、"+36 主属性"被当成 "+36%"：一点属性都没算

`increasing your Primary stat by 36` 里的 "your Primary stat" 不在白名单，
解析器走 `notes.append(f"{what} +{num}%")` —— **无条件补了个 %**。
于是胸甲附魔（Mark of the Worldsoul）既没进属性，又显示成"主属性 +36%"。
现在：剥掉 "your"、识别 "primary stat" → 存成 `main`，由 `calibrate.enchant_values`
按职业落到敏捷/力量/智力上（猎人的 +36 是敏捷）。

### 三、触发特效被当成百分比

`increasing your Critical Strike by 99 for 15 sec` → 旧正则只看到 `by 99`，
写成 "暴击 +99%"，还丢了持续时间。现在检测数值后面的 `for N sec`，
记成"触发：暴击 +99，持续 15 秒"，**不进面板**（它是 proc）。
另一种写法 `providing you with 53 Primary Stat for 15 sec` 单独一条正则。

### 四、闪避/吸血被塞进常驻属性

`bucket = tertiary if code in TERTIARY else stats` —— TERTIARY 的键是英文名
（"avoidance"），而 code 是内部代码（"avoid"），永远匹配不上。
结果所有闪避都被算进面板。改成按内部代码判断。

### 数据源的两条教训

- **wowhead 的 `dataEnv=1` 参数会让一部分物品 404**，去掉反而能拿到；
  而且请求一多会整体限流（连 19019 都 404），隔十几分钟未必恢复。
  所以这次改成 `--reparse`：用已经存下来的 tooltip 原文重算，不联网。
- **wowhead 的网页是 CloudFront 403（国家封锁）**，`nether.wowhead.com` 的
  tooltip 接口才是能用的那条；SpellItemEnchantment 的数值在 DBC 里可以自己算
  （`budget * coeff`，budget 来自 `sc_scale_data.inc` 的 level 表）。

### 验证

- 测试 163 → **171**：触发类不算常驻、主属性记成 main、腿部 6 条、
  胸附魔 +36 敏捷落到职业属性、样例附魔合计变成 耐力 219 / 敏捷 128。
- 截图核对：腿部 6 张卡都有数值、武器 10 条都写清触发效果，没有"无属性"了。
- 面板总值不变（2861/42612）——之前这两块没算，差值都压在 base 里。

## 第十九轮（紧急）：导出被 Raidbots 判为 Unverified Input

用户把导出的 simc 粘进 Raidbots，直接报
`"Load from SimC Addon" input is not valid. Make sure you are using valid /simc input`。

### 根因：`to_simc()` 把所有注释行删了

插件导出是这样开头的：

```
# 尛柒誒 - Beast Mastery - 2026-10-30 00:52 - CN/凤凰之神
# SimC Addon 12.1.5-03
# WoW 12.1.5.70575, TOC 120105
# Requires SimulationCraft 1000-01 or newer
```

结尾还有 `# Checksum: ...`。而 `to_simc()` 里写着

```python
if not line or line.startswith("#"):
    continue
```

——装备行一行没动，但整段文本**没有任何插件标识**，Raidbots 认不出这是插件导出。
（用户截图里第一个装备行是第 21 行，而原文第 21 行还是 `# Saved Loadout` 之类，
正好说明注释被削光了。）

### 改法

注释、空行、`### Gear from Bags ###` 之后的内容，现在一律原样搬运。
另外换过的部位，头顶那行 `# 中文名 (装等)` 也跟着改成新装备的名字和装等，
否则把导出的文本再导回来，界面上显示的还是旧名字。

### 验证（可自查的判据）

**什么都没改的时候，导出必须和原文逐字节一致**——实测 191 行 diff 为 0，
只有结尾多一个换行。改过的部位只差那几行。这条写成了测试：`导出保留插件头`
（`# SimC Addon` / `# Checksum` / 空行都在）、`导出能导回来`（id/宝石一致、零告警）、
`换装后注释同步`。测试 171 → **179**。

### 教训

"从零拼会丢字段"这个判断是对的，但**只保住了装备行，没保住注释**。
对 SimC 来说注释无意义，对 Raidbots 的输入校验却是身份标识——
**格式里"没用的行"可能是别人识别你的依据**。以后改导出先 diff 原文，
把"什么都没改时逐字节一致"当硬指标。

### 顺带

- `VERSION` 0.9.0 → **0.9.1**，重打了内测包（v0.9.0 有同样的问题）
- 打包版的 `/api/sample` 用的是构造样例（没有插件头），所以别拿它测导出校验，
  要用真实 `/simc` 文本测

## 第二十轮（紧急续）：`# Checksum` 没重算，Raidbots 仍判 invalid

补上头部注释后，用户反馈**还是** `input is not valid`。发现插件结尾还有一行
`# Checksum: <adler32>`，校验的是**这一行之前**的全部字节：

```lua
-- core.lua
local checksum = adler32((simulationcraftProfile:gsub("||", "|")))
simulationcraftProfile = simulationcraftProfile .. '# Checksum: ' .. string.format('%x', checksum)
```

我们改了装备却原样留着旧值 → 校验失败 → 整段仍被判无效。
（插件自己的注释也写了："lightweight verification that the input hasn't been edited"。）

**验证算法**：对 my_profile.txt 取 `# Checksum:` 之前的内容做 `zlib.adler32`
（UTF-8 字节），得到 `d5ed75c8`，和文件里的值逐位相同。所以就是标准 adler32、
小写十六进制、范围含结尾空行。

### 改法

`to_simc()` 现在把原来的 `# Checksum` 行摘掉，按新内容重算再写回去：

```python
payload = body + "\n"
digest = zlib.adler32(payload.encode("utf-8")) & 0xFFFFFFFF
return f"{payload}# Checksum: {digest:x}"
```

### 验证

- 未改动时导出与原文**逐字节一致**（含 checksum 那一行）——191 行 diff 为 0
- 改过装备后：checksum 自洽且是新值（`a55a66a0`），头部仍在
- 测试 179 → **182**：`导出校验和` 一组（未改动逐字节一致 / 改后自洽 / 值变了）
- 版本 0.9.1 → **0.9.2**，重打内测包

### 教训

**"格式里看着像装饰的东西"可能是别人的验签**。这轮连着踩了两下：
先是没有 `# SimC Addon` 头被判 Unverified，再是 checksum 不匹配被判 invalid。
以后对接外部服务，先把对方格式里每一行的作用查清楚（这次是翻插件源码才找到算法）。
另外：`Set-Content -Encoding utf8` 在 PowerShell 5.1 会写 BOM，版本号前面多一个
`\ufeff`，包名里都带着——用 `UTF8Encoding($false)` 写。

### 一、孔数不能数"插了几颗"，要数"几个位置"

第二颗连同它那个孔在界面上直接消失，于是只剩一个孔可点。

改法：`evidence = len(gem_ids) - drilled`（位置数），不再过滤 0。
`(0, 240983)` 明确说明这件装备至少两个孔。

这是"孔是位置不是数量"那条原则的**下半截**——数据层早就按位置存了，
但算孔数的地方又按数量数了一遍。

### 二、唯一宝石：永歌钻石每人限一颗

- `gems` 加 `unique_group`：按去掉品质前缀的英文名分组，

- 界面：名字后加「唯一」小标；已装在别处的卡压暗 + 「已装备」，
  点了直接 toast 说明，不发请求；悬停也不预览（无效操作不该有预览）。
- 目前只对 `kind == "diamond"` 生效。数据源（ItemSparse 的 LimitCategory）
  下载一直被截断，没等它——按用户给的规则先做，等拿得到表再扩到所有唯一类宝石。

### 验证

- 测试 182 → **190**：拔一颗孔还在（孔数、第一孔空位、第二颗原位）、

## 第二十三轮：面板基准按「职业:专精」分开（v0.9.5）

用户指出：一个职业有不同专精，基础属性得区分。

### 问题

`data/panel.json` 原来是**一份全局面板**。base = 面板 − 装备合计，
换专精之后这份面板还是被沿用：

- 混合职业主属性会换（圣骑神圣=智力、防护/惩戒=力量；萨满元素=智力、增强=敏捷），
  拿力量的面板去显示智力专精，整套数字都是错的；
- 就算主属性相同（猎人三系都是敏捷），天赋也随专精变，基础值不一样。

### 改法

- `panel.json` 的键改成 `hunter:beast_mastery`、`paladin:holy` 这种；`store.py` 里
  统一负责读写（`panel_key()` / `load_panel(key)` / `save_panel(key, panel)` / `load_panels()`）。
- `session.py` 里原来**自己抄了一份** load_panel/save_panel（和 store.py 重名，
  实际生效的是 session 里那份），这次删掉，统一走 store。
- 导入没校准过的专精时**不再借用别的专精**：panel 空 → base 空 → 顶部显示
  "未校准面板 · 只算装备本体"。这是刻意的，拿兽王的 base 显示生存的装备更害人。
- 面板弹层加一行说明：当前是哪个专精、有没有校准过、还有哪些专精校准过。
- snapshot 多返回 `panel_key` / `panel_specs`（后者带中文标签，如"猎人 · 野兽控制"）。
- 老格式（顶层直接 `agi/sta/...`）第一次读取时自动认领给当前专精并改写成新格式，
  避免升级后所有专精都能读到同一份。

### 验证

- 测试 190 → **200**：按专精取面板、保存只写当前专精、换专精不继承（panel 和 base 都空）、
  各专精互不影响、老格式自动迁移。测试用临时文件，不碰玩家真面板。
- 实测：导入兽王 → `hunter:beast_mastery`，面板 2861/42612 正常；
  把 spec 改成 survival 再导入 → `hunter:survival` 面板为空，敏捷 1805（纯装备）。
- 老 `panel.json` 已迁移成新格式，数值没变。
- 版本 0.9.4 → **0.9.5**，重打内测包。

### 备注

`class_primary()` 早就会按专精选主属性（`SPEC_PRIMARY` 覆盖圣骑/萨满/德鲁伊/武僧等），
这一轮补的是**基础值（base）**那一层，两者合起来才算"按专精区分"。

## 第二十四轮：没填面板时的职业基础兜底（v0.9.6）

用户问：能不能搜集每个职业裸装的初始面板，当程序的基准值。

### 数据从哪来

`gtClassStatsByLevel` / `gtRaceStats` 这几张 gt 表 wago.tools 不给 CSV（试过，
400 或超时）。能拿到的是 SimC 生成的 `engine/dbc/sc_extra_data.inc`（dbc_extract
从客户端导出的），里面有：
- `__gt_class_stats_by_level[14][120]`：每职业（含 No Class）每级 力/敏/耐/智/精
- `__gt_race_stats[]`：种族修正（血精灵 +2 智力、兽人 +3 力量这种）

新脚本 `src/build/fetch_class_base.py`：`--from-file` 读本地 SimC 源码，或直接下
SimC 仓库 zip（50MB）取单个 inc。产物 `data/raw/class_base.json`（69KB），
`build_db` 写进 `class_base` / `race_base` 两张表（1560 + 22 行）。

### 接入方式

base 现在有三档来源，优先级：面板 > 职业基础 > 无。

```python
if self.panel:            base = 面板 - 装备        # 含天赋，最准
elif not self.base:       base = class_base(职业, 等级) + race_base
```

只取**本职业真吃的那条主属性 + 耐力**——把力量/敏捷/智力全塞进去，猎人的属性条
会平白多出两条用不上的。属性条右上角标"职业基础 · 未含天赋，可校准"。

### 已知误差（写在界面和文档里）

90 级猎人裸装：敏捷 620、耐力 4600（血精灵再 +1 敏捷）。样例角色职业基础 621 +
装备 1805 = 2426，而面板是 2861——差的那 435 是天赋/专精被动（和可能过期的面板）。
所以这个兜底值**会偏低**，界面明确写"未含天赋"，不装作精确。

### 验证

- 测试 200 → **205**：职业基础来源、90 级猎人 621/4600、填面板后来源变 panel、
  换专精退回职业基础（不是兽王那份 3000）。
- 截图：导入生存猎（没校准过）→ 顶部 2426/40274，右上角"职业基础 · 未含天赋，可校准"。
- 内测包 v0.9.6 的 DB 里已带 class_base 表（运行时不依赖 data/raw）。

### 教训

`gt*` 表在公开数据站上拿不到，但 SimC 的 generated 数据里有一份现成的——
**当 DBC 直连走不通时，先看开源模拟器有没有把它转存出来**。

## 第二十五轮：职业基础值再校准 + 历史带专精（v0.9.7）

游戏 敏捷 2626 / 耐力 42210 / 暴击 1307 / 急速 290 / 精通 1142 / 全能 362
我们 2301 / 39970 / 1108 / 291 / 1199 / 332

上一轮直接用了 `gtClassStatsByLevel` 的 90 级值（猎人 620/4600），偏低 325 敏捷。

### 验证

## 第二十六轮：绿字换算按专精（v0.9.8）

用户："你这不是还没修好吗？你找不到所有职业专精绿字换算和初始属性的数据吗？"

### 数据事实（这轮确认清楚）

- **初始属性**：客户端只有 `gtClassStatsByLevel`（职业×等级），**没有专精级**。
  专精差异全部来自天赋/被动，暴雪不导出。"射击猎裸装敏捷"这种数据不存在。
- **绿字换算**：暴击/急速/全能是带递减的曲线（1307=43.41%、1065=38.15%，比值不是常数）；
  **精通是每专精一个系数**（兽王 1423=79.5% → 17.9/1%；射击 1142=20.5% → 55.65/1%，
  差 3 倍多）。系数藏在专精的 Mastery 法术数据（28MB 的 sc_spell_data.inc）里，
  解析成本高，这轮没做。

### 这轮做了什么

1. **面板值按真实数据填好**（用户截图）：
   - `hunter:beast_mastery`：agi 2861 / sta 42612 / crit 1065 / haste 121 / mastery 1423 / vers 394
   - `hunter:marksmanship`：agi 2626 / sta 42210 / crit 1307 / haste 290 / mastery 1142 / vers 362
2. **面板支持 `pct` 子表**：填了百分比就用 `评级 ÷ 百分比` 反推该专精的换算率。
   BM 反推出来正好是 27.92/25.16/17.90/53.97（和旧常量一致，互相验证）；
   MM 是 30.11/26.61/**55.65**/58.86 → 精通终于显示 20.52% 而不是 64%。
3. UI：面板弹层加一组可选百分比输入（游戏面板括号里那个数），存进 panel.json 的 pct。

### 验证

- 测试 205 → **209**：百分比反推换算率、换专精系数不同、pct 落盘。
- 实测：BM 精通 1423/17.9 = 79.50% ✓，MM 精通 1142/55.65 = 20.52% ✓。
- v0.9.8 打包。

### 教训

"绿字换算"不是一个常数，是 (等级曲线 × 专精系数) 两件事。之前把整个 hunter 当一套，
所以换个专精精通就错 3 倍。能用用户自己的面板反推是最省事也最准的办法——
比去解析 28MB 法术表划算。

## 第二十八轮：从"缝补"改成"分层 + 可更新"（v0.10.0）

用户点破了：越补漏洞越多；每次版本更新不该重做整个项目。

### 根因

游戏数值被写进代码（换算率、职业基础、精通系数散落在各处），
所以每次版本一变就得改代码，改一处漏一处。

### 拆成三层

| 层 | 内容 | 版本更新时 |
|---|---|---|
| 引擎 | 算法、导出、界面 | 不动 |
| 数据集 | data/raw/*.json + 清单 | 重拉 |
| 角色状态 | panel.json / accounts.db | 不动 |

### 新东西

- `data/versions.json`：每个数据集记 build / 来源 / 更新时间
- `src/build/versions.py`：`latest_build()`（wago api/builds）、`status()`、`major()`、`mark()`
- `src/build/fetch_static.py`：从 Raidbots `static/data/live/*.json` 拉装备/副本/赛季，原子替换
- `main.py --check-update`：打印数据集版本对照表
- `main.py --update`：只刷新过期的，再建库；服务开着会提示先关（sqlite 被锁）
- 判断粒度是「大版本」：12.1.5→12.1.7 不算过期，12.0→12.1 才算
- 实测：wago 最新 12.1.7.70668，本地 12.1.5 全部 ✓，只有 rating_curves(12.0.1) 标 ⚠ 需人工核对

### 顺带

- 历史记录按角色分组：`simc_history` 加 `char_name` 列（老库自动 ALTER），
  抽屉里分组显示"角色名 · 职业 · N 条"，每条只留专精/装等/时间
- 测试 230→**237**，账号 36→**38**

### 教训

"每次版本都要重做"的解法不是更努力地改代码，而是**让代码里没有版本数据**。
三层分开之后，更新变成一条命令，出错也只影响一个数据集。

## 第三十轮：双手武器属性少算一倍（根因）+ 基础系数重算（v0.10.2）

用户贴了完整 simc，逐件对 wowhead 后发现真凶：

### 双手武器一直按单手算

`curve.kind_of()` 对所有武器都返回 "weapon"，而 "weapon" 那档是拿
268201（**单手**战刃）采样出来的。双手武器（长柄/弓/法杖，inventory_type 17/15/26）
预算和头胸腿同级，是单手的两倍多。

对照 wowhead（321 装等）：
- 深渊巢魔的长柄大斧 268215：+167 敏捷 +3370 耐力 +190 精通
- 我们算出：69 / 1685 / 95  ← 正好一半

改法：`kind_of(db_slot, inventory_type)`，17/15/26 走 "big" 档；
`item_values()` 增加 inventory_type 参数；`resolve()` 把 row 的 inventory_type 带上。

### 基础属性系数分成两条

修完武器之后重新反推：主属性要 ×1.43、耐力只要 ×1.03
（之前统一 ×1.5 是在补偿武器的亏空，所以耐力虚高）。
`class_base.json` 的 `_meta.scale` 改成 `{"main":1.43,"sta":1.03}`。

### 结果（生存猎 328.2）

| | 我们 | 游戏 | 差 |
|---|---|---|---|
| 敏捷 | 2612 | 2614 | −2 |
| 耐力 | 41029 | 41014 | +15 |
| 急速 | 105 | 105 | 0 |
| 全能 | 348 | 348 | 0 |
| 精通 | 1615 | 1636 | −21 |
| 暴击 | 948 | 1033 | **−85** |

# 数据与建库

> 根 README 只留骨架，这里讲数据从哪来、怎么筛、怎么建库、表长什么样。
> 每个 `data/` 文件的性质和能否重建，见 `data/README.md`。

## 六个数据源

每个负责一块，互相不重叠：

| 源 | 提供 | 需要代理 |
|---|---|---|
| **Raidbots 静态数据**（`raidbots.com/static/data/live/`） | 装备/副本/赛季/套装/升级轨道的主数据，和 SimC 同源，直接从客户端 DB2 导出 | 否 |
| **wago.tools** | 图标 BLP（按 FileDataID）、ItemSparse 里的中文名、最新 build 号 | 否 |
| **wowhead tooltip** | 宝石/附魔的数值、装备插槽数 | **是** |
| **Maxroll** | 90 级绿字换算率与递减档位（大版本人工核对） | 否 |
| **SimC 源码** | `permanent-enchant.inc`（附魔 id 映射）、`sc_extra_data.inc`（职业 gt 表）、`trait_data.inc`（天赋节点） | 是（GitHub） |
| **客户端法术表** | 各专精的精通系数（人工整理成 `专精精通系数表.md`） | 人工 |

为什么装备主数据不用 KeystoneLoot：它只有 M+ 和团本，缺地下堡和制造业。Raidbots 的数据里
`Delves Season 2`、`Prey Season 2`、`Epic Profession Items` 都有，覆盖更全。

**每个数据集记着自己的版本**（`data/versions.json`），`--check-update` 会告诉你哪个过期了。
代码里没有一个游戏数值，所以换赛季只需要重拉数据（见根 README「版本更新」）。

## 只留当前赛季：11 万件砍到 1357 件

Midnight 资料片共 3486 件有属性装备，其中当前赛季（mid2）1357 件。筛选不是硬编码副本 ID，而是：

1. `seasons.json` 里 `active: true` 的那个赛季就是当前赛季
2. 它的 `bonusListGroups`、聚合伪实例（`-102 Season 2 Raids`、`-98 Delves Season 2`）给出内容范围
3. 用 **encounter 交集** 把真实副本（如 `1320 The Venomous Abyss`）映射回赛季

补丁换赛季后重跑即可自动跟上，不用改代码。

### ⚠ 判据不能只看资料片编号

暴雪每赛季会把**老副本复刻进 M+ 池**。本赛季的 8 个 M+ 本里有 3 个是老副本：

| 副本 | 原始资料片 | 掉落装备 |
|---|---|---|
| Kings' Rest | BfA (7) | 33 件 |
| Temple of Sethraliss | BfA (7) | 33 件 |
| Ruby Life Pools | 暗影界 (9) | 20 件 |

这些装备的 `expansion` 是 7 或 9，`itemLevel` 还停在当年的 59 / 250，**但副本在本赛季
M+ 池里，掉落时按本赛季装等算**，玩家一样能拿到、一样能转化套装。

一开始用 `expansion == 11` 过滤，把这 86 件全漏了。后果很具体：玩家身上一件套装件的
源装备是 `239035 Sethraliss' Fanged Helm`（Temple of Sethraliss 掉的），库里查不到，
套装追踪只能靠"最接近"猜。

正确判据是 `classify()` 的赛季归属，`expansion` 只用于给界面标注"这是复刻本"。
现在库里 expansion 7 有 66 件、expansion 9 有 20 件，都是本赛季能刷到的。

## 表结构速查

| 表 | 说明 |
|---|---|
| `items` | 装备主表。`slot` 已规范化（head/chest/finger/trinket/main_hand…）；`craft_kind` 标出属性由玩家选的装备（`crafted` / `boe`）；`has_sockets` 是孔数 |
| `item_stats` | 属性比例。`is_crafted_optional=1` 表示自选属性槽（stat_id 24/25），数值是槽位预算不是属性值 |
| `item_sources` | 来源。**一件装备可有多条**（M+ 装备同时挂具体副本、M+ 池、普通副本） |
| `content_pool` | 当前赛季的副本/BOSS 清单，可直接做筛选下拉 |
| `ilevel_tracks` | 装等阶梯（30 档） |
| `class_base` / `race_base` | 每职业每级的裸装基础属性 / 种族修正（含 `_meta.scale`） |
| `spec_mastery` | 每专精的精通系数 |
| `gems` / `enchants` | 宝石 / 附魔。`gems.unique_group` 标唯一宝石分组 |
| `icons` | 图标名 → FileDataID（37130 个） |
| `item_set_bonus` | 套装效果 |
| `meta` | 键值对：赛季、build、`rating_curves`（换算表）、建库时间 |
| `v_items` | 视图：装备 + 属性文字，方便直接查 |

### 怎么判断"这个职业能不能穿"

原始数据的 `specs`（专精）字段只覆盖 5%，`classes`（职业）只覆盖 28%——只有职业套装才有
这些标记，通用装备是空的。所以不能靠它们筛选。

改用两个百分百可靠的推导字段：

- `armor_type`：`cloth` / `leather` / `mail` / `plate`，来自 `item_sub_class`。戒指、项链、饰品、
  披风为 NULL（不限护甲类型）。
- `primary_stat`：`str` / `agi` / `int` / `str_agi` / `agi_int` / `str_int` / `any`，
  来自属性里的主属性 ID（3=敏捷 4=力量 5=智力 71-74=组合）。

组合判断即可：板甲+力量的装备，战士能穿，法师不能。

常用查询：

```sql
-- 当前赛季某个槽位的所有史诗装备
SELECT name, category, stats_text FROM v_items
 WHERE is_current=1 AND slot='head' AND quality=4 ORDER BY category;

-- 某件装备在哪个 BOSS 掉
SELECT instance_name, encounter_name FROM item_sources WHERE item_id=268196;

-- 地下堡能拿到的装备
SELECT name, stats_text FROM v_items WHERE is_current=1 AND category='delve';
```

## 建库

```bash
python main.py --build      # 约 10 秒，会先删掉旧的 wowgear.db
```

流程：读 `data/raw/` → 按赛季筛选 → 算孔位/归类宝石/载入附魔和中文名 →
写入 `class_base` / `race_base` / `spec_mastery` / `meta.rating_curves` → 落盘。

⚠️ 重建只碰 `wowgear.db`，**不动** `accounts.db`——账号、历史、配装存档不受影响。

具体每个数据集由哪个脚本刷新，见 `src/build/README.md`。

## 添加自定义装备

官方数据覆盖不到的（装绑、世界掉落、任务奖励、下版本新内容），用管理工具补：

```bash
# 先找图标，只列本地已下载的
python src/build/manage_items.py icons --search plate --local

# 添加
python src/build/manage_items.py add \
  --name "熔火护腕" --slot wrist \
  --stats str=1200,sta=2400,haste=900 \
  --icon inv_bracer_plate_raidwarrior_d_01 \
  --source "装绑 / 拍卖行"
```

自定义装备 `is_custom=1`，ID 从 9000000 起，和官方装备同表，界面不用特殊处理。
注意它存的是**绝对属性值**，不参与官方装备的装等缩放。

## 图标

链路：`图标名 → FileDataID → wago.tools CASC → 游戏原始 BLP → 解码 PNG`。

`src/build/icons.py` 是自己写的 BLP2 解码器（环境里没有 Pillow，BLP 又是暴雪私有格式）。
支持 DXT1/DXT5/BGRA。

FileDataID 来自社区维护的 [wow-listfile](https://github.com/wowdev/wow-listfile)，
已提取成 `data/raw/icon-index.csv`（1.4MB，37142 个图标）。这个清单比 Raidbots 自带的
`icon-paths.txt` 新——后者只覆盖 11% 的当前赛季装备。

图标文件有两种扩展名，取用时先找 `.png` 再找 `.jpg`：

- `.png` 来自 CASC 原始 BLP，64×64，质量最好
- `.jpg` 来自暴雪渲染接口，56×56，作为快速兜底

### 坏图标是怎么产生的，怎么查

下载过程会出现"文件存在但内容是坏的"，有三种，隐匿程度递增：

| 类型 | 成因 | 表现 | 怎么查 |
|---|---|---|---|
| 全透明图 | BLP 被截断，解码器无数据可解 | 一块空白 | 解压后像素只有极少种取值 |
| 半张 JPEG | 下载被截断，丢了 EOI 标记 | 只显示上半截 | 检查文件末尾是否有 `FFD9` |
| **半张 PNG** | BLP 被截断，解码器**仍按完整尺寸输出**，缺的部分留成透明 | 上半截有画、下半截空白 | 只能靠**内容**判断（见下） |

第三类最坑：它是合法 PNG，IEND 齐全、解压后字节数也吻合，任何结构检查都放行。
必须解码像素看内容分布：DXT 按 4×4 块解码，截断必然发生在 4 行对齐处，所以判据是

> 内容从第 0~2 行开始 且 最后一个有内容的行号 ≡ 3 (mod 4) 且 底部至少空 4 行

真实图标的底边是剪影形状，几乎不会正好齐平在 4 的倍数行上。实测 45 个命中，
重新下载后**没有一个是字节相同的**，说明判据没有误杀。

`src/build/check_icons.py` 不依赖任何图像库，自己解 PNG（含 5 种行过滤器）和读 JPEG 段：

- PNG：IEND、IHDR 尺寸、像素数据长度、不透明像素占比、**内容垂直分布（截断判据）**
- JPEG：EOI 结束标记、SOF 里的真实尺寸

```bash
python src/build/check_icons.py          # 只体检，列出问题
python src/build/check_icons.py --fix    # 删掉坏文件并写入重试清单
python src/build/fetch_icons.py --retry  # 重新下载
```

`icons.py` 解码时校验数据长度是否够画出整张图（不够直接返回 None），`fetch_icons.py` 校验
JPEG 首尾标记和输出大小，所以新下载的不会再产出残缺图。

**当前状态：428 个装备图标全部通过质检（0 坏图）**，另有 39 张宝石图标、3 张附魔图标
分放在 `data/icons/gems/` 和 `data/icons/enchants/`。剩下的拿不到是因为源数据把名字
写错了（`inv__misc_herb_marrowroot_leaf` 多一个下划线，游戏里不存在这个文件）。
界面遇到缺图标会显示品质色占位，不会留白。

wago.tools 的 CASC 接口不稳定，同一个文件有时超时有时成功，所以 `--retry` 多跑几轮能捞回
大部分（重试已加到 4 次、单次 35 秒）。另外这个接口必须加 `--http1.0`：走 HTTP/2 时数据
发完不关连接，curl 会一直等到超时，拿到的还是截断数据。

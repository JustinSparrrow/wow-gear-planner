# 计算与数据口径

> 根 README 只留骨架，这里讲「一个数字是怎么算出来的」以及路上踩过的坑。
> 设计层面的取舍看 `技术路线.md`，改代码看 `src/wowlib/README.md`。

## 全景：一个属性数字要经过四层

```
simc 文本 → 装备对象 → alloc 万分比 → 单件数值 → 全身合计 → 面板显示
            解析        存库          曲线换算     加宝石附魔    加 base
```

四层各自有独立的坑，下面逐层说。

## 第一层：simc 解析

```bash
python src/wowlib/simc.py tests/my_profile.txt     # 读文件
python src/wowlib/simc.py -                            # 从标准输入读（粘贴后 Ctrl+Z 回车）
python src/wowlib/simc.py xxx.txt --json               # 机器可读
```

输出：角色职业/专精、16 个槽位的装备、装等、属性分配，以及一行属性合计。每件装备都会对照
数据库校验，命中打 `✓`，缺装等或职业穿不了打 `!`，库里没有打 `✗`。

### 格式上四个必须知道的点

每行 `键=值`，装备行长这样：

```
head=Corroded Hulk's Skullcap,id=249305,bonus_id=6652/12667,ilevel=318,gem_id=240967,enchant_id=7961
```

1. **`id` + `bonus_id` 才唯一确定一件装备实例。** 同一个 id 配不同 bonus_id 就是不同装等/
   不同属性版本，所以 bonus_id 必须原样保留，不能拿 id 反查完就丢。

2. **`ilevel=` 会直接覆盖最终装等。** 这是「规划未来装备」的钥匙：想算「如果我拿到 334 的版本」，
   改这一个数字就行，不用反推 bonus_id 组合。这也是为什么装等列**只认 simc 写的 ilevel 或
   bonus_id 反查到的升级档，绝不回退到库里的 `raw_ilevel`**——后者是"裸机装等"
   （S2 团本装备记作 219），显示出来差着几十级。

   > 注意：**国服插件的真实导出根本不写 `ilevel=`**，装等全靠 `bonus_id` 推。而升级轨道表
   > 只覆盖到 334，341 这种更高档位查不到。所以解析器还会读每条装备上方那行注释
   > `# 中文名 (341)`——那是客户端本地化名 + 真实装等，可以兜底装等，顺便把中文名也解决了
   > （库里 `name_cn` 还是空的）。优先级：`ilevel=` > `bonus_id` 反查 > 注释。
   > 三个来源之间只要有两个同时存在且不一致，就报警。

3. `bonus_id` / `gem_id` / `crafted_stats` 用 `/` 分隔多个；空宝石孔写作 `gem_id=0`，解析时丢掉。

4. `### Gear from Bags ###` 之后是背包里的东西，不是当前装备。名字里自带的逗号也要保住
   （用「逗号后面紧跟 `键=`」来切分，而不是简单按逗号切）。

### 三个容易算错的地方

**主属性多形态。** 数据里 `力量/智力` 这种是「按职业自适应」，实际只出其中一个；有些装备还
同时挂了力量行和智力行（职业自适应装备），两种都加进去属性会直接虚高一倍。所以按
`职业 + 专精` 收成一个：神圣骑士吃智力、防护/惩戒吃力量，元素萨满吃智力、增强吃敏捷。

**制造业的自选槽。** `stat_id` 24/25 是"造的时候自己选"，alloc 是个整块预算（能看到 17000 这种数），
不是属性值。显示成 `+自选×N`，不计入合计。

**属性重定向（`redirected_base_stats`）。** 12.x 新字段，指向另一件装备——**这件装备的属性表
要按目标装备算，不能用自己的**。猎人头上有 5 件带这字段，其中 4 件如果用自己的表会凭空多出
1.6 万急速（面板显示却只有 4.81%）。目标装备可能是老资料片的（有一件是 BfA 的），
库里没有，所以代码会回 `equippable-items.json` 兜底取。

## 第二层：属性存比例，不存数值

数据库里 `item_stats.alloc` 是**万分比权重**，不是最终属性值：

```
属性 = alloc × 预算(装等, 部位, 品质) × 0.0001 × 评级倍率
```

同一部位同品质的 alloc 总和恒定（护甲头 20148，单手武器 25389），所以 alloc 本质是
"属性分配比例"。好处是：**一件装备只存一行，就能算出它在任意装等下的属性**，装等变了比例不变。

这也解释了为什么不能直接用 `equippable-items.json` 里的 `itemLevel` 字段——那是未加成的裸值
（S2 团本显示 219，实际玩家看到 305+）。

### 装等挂在"升级轨道"上

实际装等由纹章升级轨道决定，单独一张 `ilevel_tracks` 表：

| 轨道 | 装等 | 纹章 |
|---|---|---|
| Adventurer | 266 → 282 | 冒险者雾冠纹章 |
| Veteran | 279 → 295 | 老兵雾冠纹章 |
| Champion | 292 → 308 | 勇士雾冠纹章 |
| Hero | 305 → 321 | 英雄雾冠纹章 |
| Myth | 318 → 334 | 神话雾冠纹章 |

每轨 6 个升级档，共 30 档。用户在界面上选"我要按哪个轨道算"，比猜精确掉落装等更可靠。

### 341 / 344 装等

升级轨道表只到 **334（Myth 6/6）**。341、344 属于**特殊装等**（团本尾王 / 大秘境高层的额外档次），
不在标准轨道里，`bonus_id` 查不到。现在的处理是**用插件注释里的 `# 名字 (341)` 兜底**。
以后做选装规划时，直接手填 `ilevel=341` 即可，不需要轨道表。

## 第三层：三条曲线，五类部位

一开始以为全属性共用 `RandPropPoints` 一张表，对不上以后又以为是"两档部位"，
结果都不对。拿 wowhead 的真实数值逐件比才看清：**主属性、耐力、绿字是三条不同的曲线；
部位也不止两档，"没有主属性的部位"还要单独算**。

331 装等实测（系数 = 每万点权重折多少属性）：

| 类别 | 部位 | 主属性 | 耐力 | 绿字 |
|---|---|---|---|---|
| big | 头 胸 腿 | 349.4 | 4,788.0 | 283.9 |
| mid | 肩 手 腰 脚 | 261.0 | 3,591.1 | 212.5 |
| small | 腕 背 | 195.9 | 2,693.3 | 159.3 |
| jewel | 颈 戒指 饰品 | —（无主属性） | 2,693.3 | **227.6** |
| weapon | 主手 副手 | 144.4 | 2,393.5 | 142.1 |

几个容易踩的点：

- 主属性这些数和 `RandPropPoints` 的档位 0/1/2 完全吻合（331 装等档位 2 = 196.13，
  实测护腕 195.9）。**但绿字不是表里任何一档**——它是独立的、近乎线性的曲线，
  和主属性的比值随装等变化（250 装等时比主属性还高，344 装等只有 0.76 倍）。
  拿主属性系数硬算绿字，331 装等会高估 22%，低装等又反过来偏低。
- 耐力是主属性的 13～14 倍，也是独立一条线。
- **jewel 那一档是独立的**：项链/戒指/饰品没有主属性，绿字预算被补偿到腕/背的
  1.42 倍。不单独分出来，戒指的绿字会少算三成（8750 权重算出 139，游戏里是 199）。
- 饰品**有**主属性（比如敏捷主动饰品），所以采样拿不到系数时要回退到 small，不能当 0。

### 这张表怎么来的

`tools/sample_curve.py` 拿五件代表性装备（头 / 肩 / 护腕 / 戒指 / 主手）反复问 wowhead
（只改装等参数），把返回值反算成系数，每 4 个装等采一个点，存进 `data/stat_curve.csv`，
运行时线性插值。

**样本部位必须核对 `slot` 字段，不能看英文名猜。** 第一版拿 `Soulslither Spaulders`
（肩）当"大件"，得出"头和脚同档"的错误结论，结果头胸腿全用成中件系数，
腿的绿字少算 25%（74，实际 99）。

验证（331 装等，和游戏里的截图逐件对照）：

| 部位 | 算出 | 游戏里 |
|---|---|---|
| 护腕（制造业） | 敏捷 103 / 耐力 2,125 / 56+56 | 103 / 2,124 / 56+56 |
| 腿（制造业） | 敏捷 184 / 耐力 3,777 / **99+99** | 183 / 3,777 / 99+99 |
| 戒指（制造业） | 耐力 2,125 / **199+199** | 2,124 / 199+199 |
| 头部（掉落） | 敏捷 184 / 耐力 3,777 / 116+82 | 183 / 3,777 / 116+82 |

误差只有 ±1，来自采样间隔内的插值。

### 制造业装备和掉落装备差在哪

**数值预算完全一样，差的是分配方式和机制。**

同样装等的头部，权重总量都是 20148：

| | 耐力 | 主属性 | 绿字 |
|---|---|---|---|
| 制造业（Farstrider's 头） | 7889 | 5259 | **3500 + 3500**（两条各占一半，可自选） |
| 掉落（Hood of the Slithering Loa） | 7889 | 5259 | **4100 + 2900**（固定主次） |

戒指也一样（25389）：制造业 8750+8750，掉落 10250+7250。

所以**同装等的制造业和掉落装备，属性总量相等**（331 装等护腕实测：制造业 56+56，
掉落 34+77，合计都是 112）。区别在：

- 制造业的绿字是**自选**的，选两条就 50:50 平分，选一条就全给
- 制造业可以**再造**（recraft）改属性、改装等，掉落不行
- 制造业有 `Embellished` 特效，每人限装 2 件
- 制造业不能用勇气石升级，装等由制作时的品质和附加材料决定

界面上因此把制造业的自选槽单独标出来：选过的显示真实属性，没选的显示「自选槽 125 × 2」，
点下去会弹属性选择。

## 第四层：宝石和附魔

装备本体之外还有两块会加属性，而且**不在装备属性表里**——同一件戒指插什么宝石、附什么魔，
是玩家各自决定的。这两块以前一直解析出来却没参与计算，是面板对不上的主要原因：
样例角色光四颗宝石就少 21 点精通。

宝石比想象中给得多：一颗双属性宝石是 `+16 暴击 & +7 精通`，戒指项链腰带头各插一颗，
加起来就是几十点绿字。三色宝石（Eversong Diamond）给的是 `+32 主属性`，
要按角色的职业落到敏捷/力量/智力上——猎人那颗和法师那颗在库里是同一条记录。

### 附魔分三类，算法完全不同

| 类型 | 例子 | 怎么处理 |
|---|---|---|
| 常驻属性 | 脚 `+186 耐力`、胸 `+36 主属性` | 直接加进面板 |
| 第三属性 | 头 `+44 吸血`、肩 `+132 吸血` | 不进六属性面板，但界面上要显示 |
| 百分比特效 | 戒指 `暴击效果 +1%` | 只写说明，**不能**当 +1 暴击 |
| 触发特效 | 武器 `触发：急速 +99，持续 15 秒` | 只写说明，**不能**当常驻 |

第二条是最容易踩的坑：`critical strike effectiveness by 1%` 里也有 "critical strike"，
正则偷懒的话会解析成 `crit +1`，看着像没问题，其实整条算错了。

第四条以前也是错的：解析器把 `increasing your Critical Strike by 99 for 15 sec` 的
`99` 记成了 `+99%`，还丢了"持续 15 秒"，卡片上显示"无属性 · 特效：暴击 +99%"。
现在会写清"触发 + 持续"，没有常驻属性的武器附魔不再是"无属性"。
`+36 主属性`也是后补的：它以前被当成"主属性 +36%"进了说明，**一点属性都没算**。

### 数值是怎么拿到的

客户端 DBC 里 `SpellItemEnchantment` 的 `EffectPointsMin` 全是 0，真值靠 `ScalingClass`
缩放，自己推容易差一截。所以走**附魔卷轴的物品说明**——那是玩家在游戏里看到的文字，
也就是权威值：

```
Permanently enchants boots with Lynx's Dexterity,
increasing Avoidance by 15 and Stamina by 186.
```

三步映射（`src/build/fetch_gems_enchants.py`）：

```
permanent-enchant.inc   enchant_id → enchant_boots__lynxs_dexterity
ItemSparse              名字 → 卷轴 item id（取 580 品质那档）
wowhead tooltip         卷轴 id → 说明文字 → 结构化的属性
```

名字要先归一化再比：inc 里写 `lynxs_dexterity`（撇号被吃掉），卷轴叫 `Lynx's Dexterity`；
`farstriders_hunt` 对 `Farstrider's Hunt`（少个 s）。压成 `lynxsdexterity` 这种形式再比，
否则四十多条里会漏掉二十多。

**为什么取 580 品质**：DBC 里同一个附魔有 rank1 / rank2 两个 id，名字带 `Tier2` 图标。
实测 7961(rank2) 的系数 × 26.9 = 44，正是 580 卷轴的数值；595 卷轴是 55（Tier3）。
Tier3 在 DBC 里**没有独立 id**，所以 SimulationCraft / Raidbots 用的也只能是 Tier2。
跟着它取 580，才能保证"本地算的数字"和"导出 simc 去 Raidbots 跑出来"一致。

顺带验证了系数分组：主属性 / 耐力那一档 S ≈ 26.9，绿字那一档 S ≈ 30.8——
正好对上前面"三桶各走一条曲线"的设计。

**腿部有附魔，而且是护甲片/魔线。** 这类东西不叫 "Enchant XXX - YYY"，
物品名就是「森林猎手的护甲片」，所以按 "Enchant " 前缀筛卷轴的老逻辑一条都收不到，
腿部位一直空着。现在补了 6 条（3 个护甲片 + 3 条魔线），数值取自客户端
`SpellItemEnchantment` 的 `ench_coeff` × 580 档基数 26.99（和库里其余附魔同一基准）；
界面卡片上悬停能看到"数值按客户端附魔系数推算"。**这 6 条的数值需要游戏内核对**，
其余 38 条是 wowhead tooltip 抓下来的原文。

**某个部位一条附魔都没有时，界面要分清两种情况**：**这件装备上的附魔没收录**，和
**这个部位本来就没有附魔**，并列出本赛季收录了哪几个部位各几条。以前两种情况共用一句
"没有可附的魔"，玩家会以为游戏里腿部真没附魔。

## 宝石：孔是位置，不是数量

这块返工过三次，每次都是同一个认知升级，值得单独写。

```python
gem_ids = (240908, 0, 240983)    # 三个孔，中间那个空着
```

**空孔用 `0` 占位，数组不压紧。** 以前拔掉第 1 颗会用 `pop`，第 2 颗就顶到第 1 个孔上——
数值没错，但界面上宝石跳了个孔，导出的 simc 也把位置写错了。SimC 自己就是拿 0 表示空孔
（`ref/item.cpp` 里 `range::fill(gem_id, 0)` 之后照样把 0 写进 `gem_id=`），所以这是格式
允许的写法。末尾的空孔不留，否则导出成 `gem_id=240908/0/0/0`。

**孔数也按"位置"数，不能数"插了几颗"。** 这是同一类错误的下半截：`socket_count()`
早先数的是非空宝石个数，于是把项链第一颗拔掉之后，`gem_ids` 变成 `(0, 240983)`、
孔数从 2 掉成 1——第二颗宝石连同那个孔在界面上直接消失，表现就是"两个孔只能改一个"。
现在用 `len(gem_ids)`（位置数）当证据。

**孔数是装备的物理属性。** 规则来自游戏（12.x 改过宝石系统）：

- 戒指和项链**保底一个棱彩孔**，掉的、造的、升级的都有
- 头 / 腰带 / 护腕可以用打孔器（Radiant Jewelbinder，6 个低保币）开**一个**，每件限一次
- 别的部位一个都没有；少数团本项链自带两孔

`socket_count()` 取几路证据的最大值：库里的 `has_sockets`、simc 里的 `sockets=`、
已经插着的**位置数**、加上玩家自己开的 `drilled`。

**打孔器是玩家的选择，不在物品数据里。** 同一件头盔开没开过孔，游戏里是两个状态，
`/simc` 导出也不带这个信息。所以宝石面板上给了一个「＋ 用打孔器开一个孔」——点了就多
一个空孔，能插宝石、属性照算、跟着撤销栈走；再点一次取消（孔里还插着宝石会拦住，
免得宝石凭空消失）。能开孔的部位没孔时不再是一句"插不了"，而是直接给这个按钮。

**唯一宝石每人限一颗。** 永歌钻石（Eversong Diamond）这类是唯一装备：同一颗的不同
装等版本（278 / 295）算同一颗，戴上第二颗游戏里根本穿不上。库里 `gems.unique_group`
存分组（按去掉品质前缀的英文名分组，8 颗永歌钻石各自一组），`set_gem` 会扫一遍全身，
命中同组就拒绝并说清"哪件装备上已经有一颗"；同一个孔换成另一个装等版本算替换，放行。
界面上这类宝石名字后面带「唯一」小标，已经装在别处的卡会压暗并标「已装备」，
点了直接给提示，不会白跑一次请求。

**附魔跨部位会被拦。** 头部的附魔插到戒指上，数字看着变了但游戏里根本插不上，
这种"能用但不对"比报错更害人。

改宝石附魔和换装备走同一个撤销栈：`history` 里存的是整个 `EquippedItem`，
所以 Ctrl+Z 一样能退回去，不用为它们另造一套栈——两个栈迟早会打架。

### 换装时宝石附魔跟着槽位走

`_make_item()` 会把原槽位的 `gem_ids` 和 `enchant_id` 带到新装备上。理由是换装的人
本来就会把石头抠下来重插、附魔重附。属性计算其实用不到这两个字段，
但导出 simc 时必须带上——戒指项链少了宝石，Raidbots 模拟出来凭空低一截。

孔数不够时按新装备**截断**：从两孔项链换到一孔戒指，第二颗不会跟过去。
不截断的话导出会写成"一孔戒指插着两颗宝石"，Raidbots 直接忽略，而界面上还显示着
这两颗的属性。

### 宝石名和品质用客户端的写法

「榄石、紫晶」不是字面直译的"橄榄石、紫水晶"，来自 `ItemSparse` 的 zhCN 版本。
同一颗宝石在客户端里有 **两个装等版本（278 / 295）**，名字、品质、图标一字不差，
只有数值差 1~2 点——卡片上把装等写出来，两张卡才分得清。孔位条里也带这个数字，
不然"已插的那颗是 278 还是 295"根本看不出来。

宝石按品种分成五类（榄石=急速、紫晶=精通、榴石=暴击、青金石=全能、永歌钻石/鸡血石=主属性），
卡片左侧是游戏里的宝石图标，右边挂品质（普通 / 无瑕 / 史诗）。

## 自选槽：制造业 / 装绑

有两类装备的次要属性不写在装备上，由玩家决定。库里用 `items.craft_kind` 区分：

| craft_kind | 来源 | 自选槽 | 分配 |
|---|---|---|---|
| `crafted` | 制造业 | 2 个（`24`+`25`），也可能只有 1 个 | 双槽**平分** 3500:3500；单槽一个属性占满 7000 |
| `boe` | 团本小怪掉落（可交易） | 2 个 | **一大一小**，各件不同，实测 65:35 ~ 77:23 |

**两者的总属性完全一样，区别只在分配。** 装等 334 实测：

| 部位 | 装绑（大/小） | 制造业双槽 | 制造业单槽 |
|---|---|---|---|
| 头部 | 175 / 76（总 251） | 125 / 125（总 251） | 251 |
| 肩部 | 123 / 65（总 188） | 94 / 94（总 188） | 188 |
| 颈部 | 272 / 81（总 353） | 176 / 176（总 353） | 353 |

所以想极限堆单一属性，制造业单槽最好（100%）；想两个属性均衡，制造业双槽（50/50）最灵活；
装绑只能在 65~77% 的偏斜里选。

```bash
python src/wowlib/stat_picker.py list --kind boe          # 本赛季 9 件装绑
python src/wowlib/stat_picker.py list --kind crafted      # 204 件制造业
python src/wowlib/stat_picker.py list --kind crafted --slot back
python src/wowlib/stat_picker.py pick --item 271438 --ilvl 321 --stats crit,mastery
```

**为什么要用户指定。** 同一个 item id 在拍卖行上同时有好几种属性版本（暴击+精通、急速+全能…），
世界掉落每次随机，只存 id 永远算不对。可选组合定义在 `bonuses.json` 的 `craftedStats` 里，
数组顺序就是槽位顺序：

```
6647: [32]        只选暴击
8790: [32, 36]    暴击（大槽）+ 急速（小槽）
8793: [49, 36]    精通（大槽）+ 急速（小槽）
```

`bonuses.json` 里 `encounterId = -97` 是"团本小怪掉落"的标记，本赛季 9 件装绑全在
`1320 The Venomous Abyss`。装等要用户填——装绑的装等取决于团本难度和赛季，
不在装备数据里；拍卖行上看到多少就填多少。

⚠️ **`crafted_stats` 这个字段不可信。** 导出里写着 `49/36`（精通/急速），但玩家实际选的
是全能精通。拿它算，玩家的急速会凭空多出 400 多点、全能少算一半。

所以启动时会用 `data/player_crafted.json` 里确认过的属性覆盖掉导出值，没确认过的在界面上标
`⚠`。用 `fix` 命令逐件确认，改完自动记住，下次启动直接套用。

## 套装转化：绿字保留

本赛季节气装备能通过催化转化变成套装件，**绿字原样保留**。这条规则决定了三件事：

1. **套装件自身的属性表不可信**。同一个套装头 id，从不同源装备转化过来，绿字完全不同，
   库里存的那一份只是某一版。
2. **`redirected_base_stats` 就是源装备 id**，导出里自带，属于正向链路。
3. **反查要靠绿字占比**。想知道"暴击精通的套装头该怎么弄"，就得查同部位哪些可转化源装备
   能给这对绿字。

```bash
python src/build/tiers.py --profile tests/my_profile.txt   # 身上每件套装件的源装备
python src/build/tiers.py --slot head --list               # 头部全部可转化源及绿字组合
python src/build/tiers.py --slot head --stats crit,mastery # 反查：哪些源能给暴击+精通
```

源装备可能不在当前赛季（实测有一件是 BfA 的），这时会回原始数据取它的绿字，再用**占比**
去当前赛季的候选里找最接近的几件——不同装备预算不同，比较绝对值没有意义，只能比占比。

## 命令行里的数字是什么意思

`main.py` 显示的是**装备 + 宝石 + 附魔**的合计。还差的是套装加成、天赋和 90 级自带的基础值——
那部分由 `data/panel.json` 里的面板数字兜底（`base = 面板 − 装备合计`），所以网页顶部
永远显示面板值，换装时加减的是装备那部分。

想核对装备合计算得对不对，把 `panel.json` 填成同一身装备的面板评级，
然后看 `python src/wowlib/calibrate.py tests/my_profile.txt --panel ...` 的输出：
倍率接近 1 就说明这三块都算对了。

⚠️ **`panel.json` 和导出文件必须是同一身装备。** 换了装却沿用旧面板，
两者的差额会全部压到 `base` 上，那个数就没有物理意义了（甚至会是负的）。
换装之后重新导一次 simc、重新填面板，这一步不能省。

⚠️ **面板是按专精存的，换专精别指望它自动换算。** 导入一个没校准过的专精时，
工具不会拿别的专精的基线去凑，而是直接显示"只算装备本体"。这是刻意的——拿兽王的 base
去显示生存的装备，数字看着像模像样，其实全是错的。

> 面板要填**评级**（"XXX 等级"），不是百分比。百分比混着职业基础值和天赋加成，反推会被污染。

用真实面板验证过：全能 394 / 54 = 7.30% ✓ 完全吻合；暴击 1065 / 46 = 23.15%，
面板 38.15%，差 15 正好是敏捷系基础暴击 + 天赋。

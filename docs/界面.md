# 界面说明

> 根 README 只留骨架，这里讲界面为什么长这样。
> 改界面代码看 `src/web/README.md`，改计算看 `docs/计算.md`。

```bash
python main.py --web      # 然后打开 http://127.0.0.1:8765
```

## 入口页：登录 / 注册 / 游客

打开就是全屏入口页，底图是 Midnight 官方美术图（`src/web/img/stand.jpg`，取自暴雪
新闻中心的 Stand As One key art），右下挂一张登录卡，三个出口：

- **登录 / 注册** —— 用户名 + 密码，只写本机 `data/accounts.db`，密码 PBKDF2 加盐
- **游客** —— 直接进主界面，模拟功能一样不少，只是存不了配装、没有 simc 历史

判断顺序写死在 `boot()` 里，从上往下：

| 情况 | 结果 |
|---|---|
| 带着登录 cookie 回来 | 直接进主界面 |
| 这一趟已经点过游客（`sessionStorage` 的 `wg.guest`） | 直接进主界面，刷新不再问 |
| 都不是 | 停在入口页 |

游客标记放 `sessionStorage` 不放 `localStorage`：关掉标签页就该忘掉，下次打开重新问一遍。
放 `localStorage` 的话，第一次点了游客，往后永远看不到注册入口。

游客第一次进主界面时**不读**服务端残留的那份会话——服务端虽然已经按浏览器
分开存了（见「多账号怎么隔开」），但同一台机器上上一次试的样例还挂在你的浏览器
身份下，一开门就看见一身不认识装备，会以为工具在乱用数据。
点过「游客」之后这一趟内刷新还是照常接上（`wg.entered` 标记）。

进主界面之后第一件事是导入 simc。粘进去之后自动识别职业、专精、护甲类型（猎人 → 锁甲），
右侧候选只列这个职业能穿的装备，不用手选职业。

### 平均装等

**顶栏那个平均装等是整个角色的装等**，不是当前选中部位的。算法和游戏角色面板一致：

```
平均装等 = 16 个格子装等之和 ÷ 16
```

- 空格子算 0
- **双手武器算两次**（同时占主手和副手两格）。猎人拿一把 341 的弓，武器贡献 682 而不是 341。
  不这么算，双手职业的平均装等会平白低 20 多。
- 单手武器 + 空副手，副手那一格就是 0，不补——补了就虚高
- 衬衫和战袍不算（它们不在 16 格名单里）

判断双手的依据是 `items.inventory_type`：15（弓/枪）、17（双手武器）、26（远程右手）
都算占满两只手。鼠标悬停候选卡时，这个数字会跟着变成"换上以后是多少"，涨绿跌红。

### 装备栏顺序

**左边装备栏照抄游戏里的角色面板**，顺序也是游戏里的顺序：

| 左列（上→下） | 右列（上→下） | 底排 |
|---|---|---|
| 头 颈 肩 **背** 胸 腕 手 | 腰 腿 脚 戒1 戒2 饰1 饰2 | 主手 副手 |

披风在左列第四个、手套在左列第七个——这是游戏里的位置。如果按 simc 的槽位顺序排
（头颈肩胸腰腿…背在最后），玩家每次看都得重新找一遍，装备栏就失去了"一眼扫过去"的意义。

格子按可用高度平分，铺满左栏；窗口矮的时候出滚动条，不会把格子压扁。
位置写死，没有的部位显示空槽，换装时格子不会跳。

**每个格子最下面一行是这件装备的绿字**（`精通 135 暴击 87`），按数值降序只留两条，
多的折成 `+2`，鼠标悬停看全部。主属性不在这里显示——顶部那条就是总数，单件那一两百点
看了也判断不了什么；绿字才是同一部位横向比较时要看的东西。饰品这类没有绿字的写「无绿字」，
不能空着让人以为数据没读到。

制造业和装绑的自选槽在库里的 code 只是占位（`bonus1` / `bonus2`），指定过属性后要换成
真实属性，否则数值算出来了却挂不到任何一行上，整件装备看起来只有耐力敏捷。候选列表里
还没选属性的，写「自选槽 122 × 2」而不是「待指定」——不写点数，用户没法判断值不值得换。

**属性条放在顶部**，因为换装时最想知道的就是"换完属性怎么变"。鼠标划过候选卡
就会在数值下面挂出增减（`暴击 1,150 +82`），不用点下去也能先比较。

### 交互

| 操作 | 效果 |
|---|---|
| 点左侧部位 | 右侧列出该部位全部候选，卡片直接带属性数值和差值 |
| **鼠标悬停卡片** | 属性条显示"换上后会变成多少"，左侧对应格子虚线高亮（不落地） |
| **点卡片** | **直接换上**，左侧格子立刻变，底部弹出"已换上 X"提示 |
| 点右上「装等」 | 切换候选装备按哪个装等算属性（266–344 共 24 档） |
| 点来源标签 | 只看某个来源（团本 / M+ / 地下堡 / 套装转化 / 制造业 / 猎杀） |
| 点「撤销」 | 退回上一步换装（栈深 50 步） |
| **右键部位** | 恢复该部位原装备 |
| 「全部还原」 | 一键回到刚导入的状态 |

点击即替换，没有"确认装备"这一步——游戏里点装备也是一下就穿上。怕点错有撤销兜底，
不需要每次多按一下确认。

**状态存在服务端**，刷新页面不会丢。前端只发操作指令，属性计算统一由 `session.py` 做——
如果让前端自己算一遍，预览和结算迟早会漂移，界面显示 +64 而实际 +40 这种错最难发现。
悬停预览走的也是最终计算函数（临时换上、算完放回），不是另写一套近似公式。

## 装等：每件装备都能选，不只是制造业

只有制造业和装绑能填装等是错的。同一件装备从哪一级升上来、是英雄还是神话，绿字差很多，
所以**所有候选都可以选装等**，右侧顶部的「装等」按钮弹出 24 档：

| 组 | 档位 |
|---|---|
| 冒险 | 266 269 272 276 279 282 |
| 老兵 | 279 282 285 289 292 295 |
| 勇士 | 292 295 298 302 305 308 |
| 英雄 | 305 308 311 315 318 321 |
| 神话 | 318 321 324 328 331 334 |
| **特殊** | **341**（额外升级，神话满级 +7）、**344**（神话团本尾王） |

前五组来自 `ilevel_tracks` 表。341 和 344 不在表里，是手动列的——属性预算表
（`RandPropPoints`）本身覆盖到 875 装等，这两个档位直接能算，不需要插值。

切换装等后所有候选的属性数值立刻按新装等重算，相当于"同一件装备，我要 334 的版本还是要 344 的"。
默认值是**当前这个部位身上的装等**，所以大多数时候不用动它。

## 卡片上看得到什么

一张卡四层，从上到下依次是"这是什么 / 从哪来 / 有多少属性 / 换上去值不值"：

```
┌──────────────────────────────────────────────────────────┐
│ [图] 永恒毒牙之冠                                [当前]   │
│      Crown of the Eternal Fang                           │
│      团本 · The Venomous Abyss · Nek'zali the Soulcoiler │
├──────────────────────────────────────────────────────────┤
│ 敏捷 207   耐力 310   暴击 187   精通 88                  │
├──────────────────────────────────────────────────────────┤
│ 暴击 +187   急速 −159   精通 +7                          │
└──────────────────────────────────────────────────────────┘
```

**中文名下面那行是英文名**，压暗显示。理由很具体：Raidbots 那边只认英文名，
换装前得知道这件在那边叫什么，不然去 Top Gear 里搜半天搜不到。悬停浮层里也有，
左边装备栏的悬停同理。

属性数值是按**当前选中装等**真算出来的（`alloc × 装等预算 × 1e-4`，和最终结算同一个公式），
不是把权重原样列出来。最后一行是"这件相对身上那件"的差，涨绿跌红——不用点下去就知道值不值。

卡片是两列布局：候选本来就不多（一个部位十来件），一列太窄信息挤成豆腐块，三列又会
让来源行频繁截断。两列刚好装下"副本 · boss"整行。

## 候选卡片上的来源

每张卡都写明出处，这是选装备时第二重要的信息（第一是属性）：

```
[图] Crushing Coiler Coif
     团本
     The Venomous Abyss
     Trash Drop
```

数据里一件装备往往有好几条来源记录，其中混着聚合桶：

```
Ruby Life Pools / Kokia Blazehoof     ← 真正的出处，副本地 + boss 名
Mythic+ Dungeons / Ruby Life Pools    ← 聚合桶，boss 位被填成了副本名
```

所以 `source_of()` 会先挑"instance 和 encounter 都是具体名字"的那条，挑不到才用聚合行兜底。
不做这一步，界面上就是一片 `Mythic+ Dungeons`，等于什么都没说。

来源类别按颜色区分：团本（橙）、M+（蓝）、地下堡（绿）、套装转化（紫）、制造业（黄）、猎杀（粉）。
套装转化件没有"从哪个副本转化"的对应数据，只能标到套装名（`套装转化 · Skulking Viper's Ambush`）。

## 候选里为什么没有重复的

同一部位、同一职业，一个格子对应一件装备。之前会冒出"同一件出现好几遍"的情况，两个来源：

1. **套装转化件没按职业过滤**。唤魔师、萨满、猎人都是锁甲，套装却是三套不同的，
   不过滤的话锁甲角色会看到三个"头部 · 套装转化"，属性还不一样，很容易选错。
   现在按 `items.classes`（职业 ID 的 JSON 数组）过滤，逗号包一层再 LIKE，
   避免职业 1 匹配上 11/12/13。

2. **制造业同属性重复**。工程、制皮、裁缝各做一款 197 的黄字头，属性分配一模一样
   （耐力 + 白板 + 一半自选槽），品质只决定材料。对"算属性"来说它们完全等价，
   摆七张卡纯是噪音。现在合并成一张，角标写 `同款 4`，悬停列出具体是哪几款。
   单槽 7000 和双槽 3500+3500 不合并——能自选的属性个数不同，是两回事。

团本和 M+ 的装备**不合并**：那是不同 boss 掉的不同东西，合并了就丢掉"去哪刷"。

装绑和制造业点下去会先弹属性选择：四个属性按钮选两个，装等自己填（拍卖行上标多少填多少），
弹层里还会显示这件装备的槽位比例（装绑是 66%:35% 这种一大一小，制造业是 50:50）。
确认后同样是直接换上。

## 数值口径：面板校准

顶栏右边有个「面板校准」。点开把游戏里悬停属性看到的**评级**填一遍（敏捷/耐力/暴击/急速/精通/全能），
之后顶部显示的就是"角色基础 + 装备"的真实值，能和面板对上：

```
面板敏捷 2861 = 角色基础 1096 + 装备 1765
面板耐力 42612 = 角色基础 39884 + 装备 2728   ← 耐力差得最夸张，装备只占 6%
```

不填也能用，但那时只显示装备本体，敏捷会比面板低一千多——因为天赋和等级自带的属性不在装备里。

计算方式是 `base = 面板 − 首次装备合计`，之后换装都是 `base + 新装备`。base 存在 `data/panel.json`，
填的值不依赖我们的换算公式准不准：**你填什么就显示什么**，装备只贡献增减。

### 面板按「职业:专精」分开存

换专精要重新填一次。一个职业的不同专精，基础属性本来就不一样：

- 混合职业的**主属性会换**：圣骑神圣吃智力、防护/惩戒吃力量；萨满元素吃智力、增强吃敏捷；
  德鲁伊平衡/恢复吃智力、野性/守护吃敏捷（这张对照表在 `simc.py` 的 `SPEC_PRIMARY` 里）。
- 就算主属性相同（猎人三个专精都是敏捷），**天赋也随专精变**，面板上的基础值跟着变。

早先是一份全局面板：换专精之后 base 还是按上一套算，"面板 2861"被套到另一个专精上，
所有绝对值都是错的。现在文件长这样，导入哪个专精就取哪一份：

```json
{
 "_note": "...",
 "hunter:beast_mastery": {"agi": 2861, "sta": 42612, "crit": 1065, ...},
 "hunter:survival":      {"agi": 2999, ...}
}
```

没校准过的专精显示"未校准面板 · 只算装备本体"，面板弹层会写明当前是哪个专精、
还有哪些专精已经校准过。老格式（顶层直接是 `agi/sta/...` 的扁平文件）会在第一次导入时
自动认领给当前专精并改写成新格式——但那份值原本属于哪个专精我们无从判断，
如果你是换着专精用的，建议两个专精各重新填一次。

### 没填面板时用职业基础兜底

`data/raw/class_base.json` 是从客户端 `gtClassStatsByLevel` / `gtRaceStats` 抽出来的：
每个职业每一级的力量/敏捷/耐力/智力，再叠一点种族差异（血精灵 +2 智力、兽人 +3 力量这种）。
属性条右上角会标"职业基础 · 未含天赋，可校准"。

**这张表是压缩前的标尺，要乘一个校准系数。** 证据很直接：SimC 生成的
`hp_per_sta(90) = 75`，而游戏面板里 生命值 928,620 ÷ 耐力 42,210 = **22**。用真实
90 级猎人的面板（敏捷 2626 / 耐力 42210）反推，职业基础要 **×1.5** 才对得上：

```
敏捷：620 × 1.43 + 血精灵 1 = 888  → 888 + 装备 1724 = 2612（游戏 2614）
耐力：4600 × 1.03          = 4738  → 4738 + 装备 36291 = 41029（游戏 41014）
```

系数写在 `class_base.json` 的 `_meta.scale` 里，`build_db` 只在职业那部分乘
（种族那点 ±3 是原始增量，不缩放）。换资料片、客户端重新压缩属性之后要重新拟合。

它**不含天赋和专精被动**，所以仍会比游戏低一点点（1% 量级），界面上标了"未含天赋"。
填一次面板就能完全盖过它——面板是游戏里的真值，那个才是精确的。

生成方式（换赛季/资料片、或者客户端压缩了属性时重跑）：

```bash
python src/build/fetch_class_base.py --proxy http://127.0.0.1:7897   # 自动下 SimC 源码取表
python main.py --build                                               # 写进 class_base 表
```

### 百分比：换算率 + 递减

百分比（暴击 38.1% 这种）**不再用一条直线**，而是按客户端的换算率 + 递减档位算：

| 属性 | 90 级每 1% 需要 | 递减起点 |
|---|---|---|
| 暴击 | 46 | 1380（-10%），1840（-20%）… |
| 急速 | 44 | 1320，1760 … |
| 全能 | 54 | 1620，2160 … |
| 精通 | 46 / 点 | 每点先算「精通点」：**8 基础点 + 评级/46**，再乘专精系数 |

数据源：Maxroll《Stat Diminishing Returns》12.0.1（2026-03-13），和 NGA 12.0 数据挖掘一致，
落在 `data/raw/rating_curves.json`，建库时写进 `meta.rating_curves`。

**递减是按档位分段的，只对越过门槛的那部分打折。** 急速 1320 之后那一段只按 90% 计入：

```
1320 急速（30%）再 +264 → (1320 + 264×0.9) / 44 = 35.4%   ← 官方例子
```

**精通系数每个专精都不一样**（`spec_mastery` 表，40 条）：兽王 1.9、射击 0.625、守护 1.0。
同一个猎人换专精，精通百分比差 3 倍多；以前用一条全局 17.9 算，射击会显示 64%，实际是 20.5%。

**角色自带的固定百分比由面板反推，不是常数。** 例：守护德全能 419 评级，曲线只给 7.76%，
面板是 19.76%——差的 12 点是这个专精自带的（天赋/被动）。猎人全能 394 评级正好 7.30%，
一点都没有。所以 `flat_pct()` 用「面板% − 曲线(面板评级)」算每个专精自己的偏移：

```json
{ "druid:guardian": {
    "crit": 1010, "haste": 1294, "mastery": 252, "vers": 419,
    "pct": {"crit": 31.96, "haste": 30.70, "mastery": 13.63, "vers": 19.76} } }
```

校准过的专精四项都和游戏逐字一致（守护德 31.96 / 30.70 / 19.76 / 13.63 已验），
没校准的只算曲线部分，界面会标"职业基础 · 未含天赋"。

### 套装转化件的绿字

套装转化（catalyst）件在库里存的那套属性**只是模板**，实际转化出来继承被转化那件装备的绿字。
simc 用 `redirected_base_stats` 记着源装备：

```
head=,id=271492,...,redirected_base_stats=239035
```

所以界面上：

- **身上穿着的**转化件，按源装备显示真实绿字（猎人头实际是暴击+精通，不是模板的急速+精通）
- **候选列表里的**转化件不给数值，只写"属性继承转化前的装备"和套装名——因为还不知道你要拿哪件去转

早期版本没做这个区分，猎人头部显示的是模板的急速 4993/精通 2007，而角色身上实际是暴击 2750/精通 4250，
差了整整一个属性的量。这种错不会报异常，只会让人做错决定。

## 账号、历史与配装保存

不登录也能用全部功能（换装、算属性、看来源），只是存不了东西。
右上角「登录」注册一个：用户名 2–20 字符、密码 4 位以上。

```
顶栏 [登录] → 弹窗注册/登录 → 变成 [● 用户名]
点用户名 → 右侧抽屉：我的配装 / 历史 simc
```

「历史 simc」和「我的配装」都**按角色分组**：同一个人的兽王/射击/生存是三条不同记录，
平铺在一列里等记录多了根本找不到。分组头显示角色名 + 职业 + 条数，
每条只显示专精、装等和时间（`simc_history.char_name` 是单独一列，不是从标题里切字符串）。

**为什么值得登录**：真正有用的不是登录，是两件事——

1. **导入过的 simc 自动留档**。同一份配置反复导入只更新时间，不会堆一列重复条目；
   只留最近 40 条，更老的自动清掉。每条都带**职业 · 专精 · 名字 · 装等**
   （`simc_history` 表里早就有 `spec` 列，只是列表里以前不显示）——
   同一个猎人换专精跑，几条记录全是"猎人 · 名字 · 装等"根本分不出来。
2. **调好的装备能命名保存**。点「存配装」，起个名字（默认填「角色名 · 月/日 时:分」，
   可以改），备注可选。同名保存是**覆盖**不是新增——点两次保存不该得到两套一样的。

### 存档存的是「原文 + 改动」，不是最终数值

```json
{ "base_simc": "warrior=...\nhead=...", 
  "changes": [{"slot":"head","id":268230,"ilevel":334,"crafted":[]}] }
```

存改动而不是存结果，是因为**结果会过期**：属性曲线换了、赛季更新了、装备库重建了，
存死的数值永远停在保存那天。存原文 + 改动，载入时重新算一遍就自动跟上新数据。

代价是载入时依赖库里的装备 id。赛季一换老 id 就没了，所以 `apply_changes()`
**认不出的装备跳过而不是整份失败**——能载回大半套，好过报错一套都看不到。
跳过的部位会在提示里说清楚有几个。

### 多账号怎么隔开

服务端不是"一个全局会话"，而是**每个身份一份**：

```python
STATE = {}     # key = "u<用户id>"（已登录）或 "a<浏览器id>"（未登录）
```

以前只有一个全局 `STATE["session"]`，一支持账号就出问题：A 登录着，B 打开页面
就把 A 的装备顶掉了。

后来改成"未登录的挂 `anon` 位"，其实还是错的——`anon` 仍然只有一份，所有
没登录的浏览器共用。结果是：A 在自己机器上粘了一身装备，B 打开就看到 A 的；
更糟的是 B 一登录，这套装备被"过继"进 B 的账号，账号里凭空多出一身不认识的
装备，登录后第一眼看到的不是自己的角色。

现在给每个未登录的浏览器发一个长期 cookie（`wg_aid`，一年），会话按它分开。
浏览器清 cookie 就会换一个新身份，旧的那份留在内存里直到服务重启。

两个行为：

- **登录不继承未登录的装备**。账号就是账号，没有装备就弹导入框。
  游客模式那份还在原处，退出登录能回去接着看。
- **退出登录不动任何会话**，只是让令牌失效。下次登录还能接上上次那套。

### 存储

`data/accounts.db`，独立于 `data/wowgear.db`：

| 表 | 存什么 |
|---|---|
| `users` | 用户名、PBKDF2 加盐哈希、salt |
| `sessions` | 登录令牌（30 天过期） |
| `simc_history` | 每次导入的原文 + 摘要标签 |
| `loadouts` | 配装：名称、备注、原文、改动清单 |

**账号库必须和游戏数据库分开**：游戏库会随赛季整库重建，账号重建一次就全没了。

密码只存 `pbkdf2_hmac('sha256', ...)` 的结果（迭代 12 万次）加 16 字节随机 salt，
不存明文。登录失败时"用户不存在"和"密码错误"返回同一句话，否则接口就成了用户名探测器。

越权检查写在 SQL 里（`WHERE id = ? AND user_id = ?`），不是在 Python 里比一下——
写接口最容易忘的就是这一条，`tests/test_accounts.py` 专门验了别人的存档读不到、删不掉。

## 导出给 Raidbots

模拟器只能告诉你"这一身打多少"，换一件到底强多少得跑一次模拟。所以主界面
右上角有「导出 simc」：把当前这套装备写成 simc 文本，粘进 Raidbots 的
Quick Sim 就行（弹层里有直达链接）。

实现上**逐行重写原文**，而不是从零拼：

```
没换过的部位  →  原样搬运（redirected_base_stats / content_tuning /
                crafting_quality 这些字段解析器本来就不认识，重写会丢）
换过的部位    →  ,id=X,ilevel=Y + 沿用原槽位的宝石和附魔（名字留空）
```

不这么做的两个坑：套装转化件丢了 `redirected_base_stats`，属性会算成套装模板
而不是源装备；制造业丢了 `crafting_quality`，品质档位没了。

**换过的部位绝不能写名字。** 这是整条链路上最容易踩、也最隐蔽的一个雷。
`engine/item/item.cpp` 里，装备行同时给了名字和 id 时会比对自己 DBC 里的名字：

```cpp
if ( ! option_name_str.empty() && ( option_name_str != name_str ) )
{
  sim -> error( "{} at slot {} has inconsistency between name '{}' and '{}' for id {}\n", ... );
  name_str = option_name_str;
}
```

`sim->error` 直接让整个模拟失败。Raidbots 跑的就是 simc，失败在界面上表现成
**`"Load from SimC Addon" input is not valid`**——而装备一行都没错。

游戏插件正是因此才只吐 `head=,id=271492`：中文客户端拿到的名字是中文，simc
必然不认，所以它索性一个字都不写。我们曾经"好心"把它补成英文名，正好踩中。

**注释行必须原样保留。** 插件导出是这么开头的：

```
# 尛柒誒 - Beast Mastery - 2026-10-30 00:52 - CN/凤凰之神
# SimC Addon 12.1.5-03
# WoW 12.1.5.70575, TOC 120105
# Requires SimulationCraft 1000-01 or newer
```

早先 `to_simc()` 里 `if not line or line.startswith("#"): continue` 把所有注释
丢掉了，装备一行没错整段却被拒。现在注释、空行、`### Gear from Bags ###`
段一律原样搬运。

**`# Checksum` 只在没改过东西时保留。** 插件是这么写这一行的（`core.lua`）：

```lua
local checksum = adler32(simulationcraftProfile)
profile = profile .. '# Checksum: ' .. string.format('%x', checksum)
```

校验范围是 `# Checksum:` 之前的全部字节（含结尾那串空行），值是小写十六进制的
adler32（实测原文件 `d5ed75c8` 用 `zlib.adler32` 能对上）。

这个值的作用只有一个：**给"这份文本没被改过"背书**。所以：

| 情况 | 处理 |
|---|---|
| 一件都没换 | 原样还回去，导出的文本和插件输出**逐字节一致** |
| 换过装备 / 改过宝石附魔 | **整行去掉** |

改完装备还留着它就是一张假凭证；按新内容重算同样是在冒充，而且对方无从自证。
去掉之后，Raidbots 会把它当普通 profile 处理——Quick Sim 就吃这个。

**Raidbots 三个入口怎么选。** 同一个文本框，语义不一样：

| 入口 | 接受改过的文本 | 适合做什么 |
|---|---|---|
| Quick Sim | ✅ 直接跑 | 只看这一套打多少 |
| Top Gear | ✅ 但带 `Edited` 角标 | 在新旧两件之间枚举对比 |
| Stat Weights / Advanced | ✅ | 权重、任意脚本 |

那个红色的 **`Edited`** 角标是 Raidbots 的判断结果——它发现有 `# SimC Addon` 头、
但 `# Checksum` 不见了或对不上，于是提示"这份输入被改过，结果不保证"。**它不是报错**，
反而是我们想要的信号：我们确实改过装备，标识出来才诚实。

以前这里会直接甩 `input is not valid`，那是 simc 解析失败，性质完全不同：
前者是"我认出来了，但提醒你一句"，后者是"我读不懂"。

**换过的装备还要补进背包段。** `### Gear from Bags` 整段都是 `#` 注释，插件
不往这里写真正的装备行——Raidbots 是自己解析这些注释来建"可选装备池"的，
Top Gear 的勾选框就是从这儿来的。所以导出时必须把两件都塞进去：

```
#
# 永恒毒牙之冠 (334)
# head=,id=268230,ilevel=334,enchant_id=7961     ← 你换上的（游戏里并没有）
#
# 潜伏蝰蛇的渗液之牙 (321)
# head=,id=271492,bonus_id=6652/.../12846,ilevel=321,enchant_id=7961   ← 原来那件
```

不补的话两头都看不见：换上的那件游戏里不存在，原来那件被换掉了不在身上。
Top Gear 里一件都勾不到，"原 vs 新"压根比不了。补进去才能直接跑组合对比。
注意原件那行带 `bonus_id`（原文解析出来的），新件没有——新件的装等只能靠 `ilevel`。

另外，换过的部位，它头顶那行 `# 中文名 (装等)` 也要跟着改，否则把导出的文本
再导回来，界面上显示的还是旧装备的名字。

一个可以自查的判据：**什么都没改的时候，导出的文本应该和你的原文逐字节一致**
（包括 checksum 那一行）。`tests/test_simc.py` 里有「导出校验和」和「导出行不写名字」
两组盯着这件事。

宝石附魔跟着槽位走（换装备时人会把石头抠下来重插、附魔重附），属性计算用不到
这两个字段，但导出时必须带上，否则模拟出来的属性平白少一截。

⚠️ **打孔器开的孔导不出去。** SimC 的 item 选项里没有 `sockets=`（那一串里只有
`gem_id` / `gem_bonus_id` / `gem_ilevel`，孔的多少来自它自己的物品数据），所以"额外一个孔"
在 simc 格式里根本表达不出来。导出弹层会明说哪几件用了打孔器、模拟结果会比这里少这点属性。
写 `sockets=` 出去是更糟的选择：那是个不认识的字段，Raidbots 那边会直接报错。

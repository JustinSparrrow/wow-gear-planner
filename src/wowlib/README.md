# src/wowlib — 业务层

解析、换算、一次配装会话。这一层把 `wowgear` 的核心能力串成"能对角色做点什么"。

## 文件

| 文件 | 职责 | 关键点 |
|---|---|---|
| `simc.py` | simc 字符串解析（文本→装备列表） | `id`+`bonus_id` 才唯一；`ilevel=` 覆盖装等；注释兜底装等和中文名 |
| `calibrate.py` | 装备属性合计（含宝石附魔） | `compute()` 把三块加起来；`gem_values`/`enchant_values` |
| `stat_picker.py` | 属性由玩家选的装备（制造业/装绑） | 自选槽的分配比例；`slots_of` |
| `catalog.py` | 装备目录：查一件、列候选 | 从 `wowgear` 挪来，因为要判断职业得依赖 `simc` |
| `talents.py` | 天赋导入字符串解码 | 6bit/字符的位流，节点必须按 id 升序；**尚未接入计算**，见下 |
| `session.py` | 会话：穿/预览/撤销/还原，串起上面几块 | 状态存服务端；孔位模型；百分比换算；base 三优先级 |

## 核心对象：`Session`

一个 `Session` = 一个角色当前这身装备 + 计算出来的属性。命令行（`main.py`）和网页
（`serve.py`）共用同一份，保证预览和结算走同一个函数。

它对外暴露的都是"动作"：

- `equip` / `preview_full`——换装 / 临时换上算完放回
- `set_gem` / `preview_gem`——插宝石 / 悬停预览
- `set_enchant` / `preview_enchant`——附魔 / 悬停预览
- `set_drilled`——用打孔器开/取消一个孔
- `undo` / `reset` / `reset_all`——撤销栈 / 还原
- `to_simc`——导出回 simc 文本（逐行重写原文，保住解析器不认识但 Raidbots 认的字段）

## 宝石这块的三个概念（最容易搞混）

| 概念 | 存在哪 | 谁决定 |
|---|---|---|
| **孔数** | 算出来的，不存 | `socket_count()` 取几路证据的最大值 |
| **哪个孔插什么** | `gem_ids` 元组，按位置对齐，0 = 空孔 | 玩家 |
| **打孔器的孔** | `drilled` 字段 | 玩家在界面上勾选（头/腰/腕各限一个） |

`socket_count()` 的四路证据：库里的 `has_sockets`、simc 里的 `sockets=`、
已经插着的**位置数**（不是非空数量）、再加上 `drilled`。

⚠️ 位置数是关键：`gem_ids=(0, 240983)` 说明这件装备**至少两个孔**（第一孔空着）。
早先只数非空宝石，拔掉第一颗后孔数从 2 掉到 1，第二颗宝石连同那个孔一起消失。

配套的两条规则（查证过的游戏规则，不是猜的）：

- `GUARANTEED_SOCKETS`：戒指/项链保底 1 个棱彩孔
- `DRILLABLE_SLOTS`：头/腰带/护腕能用打孔器开 1 个

## 百分比换算的三层

```python
session.stat_pct("haste", 1584)   # -> 36.0 上下
```

1. `_curve_pct()`：评级 → 百分比，走 `rating_curves.json` 的换算率和递减档位。
   **只算装备那部分**，不含任何基础值
2. `flat_pct()`：加上「装备之外」的固定百分比。两级来源，面板优先：
   - `spec_base()` 查 `spec_stats` 表——每个专精的默认基线，没填面板也有数
   - 面板反推——`面板% − 曲线%`，精确到这个角色选的天赋
3. `_rates()`：面板里带了百分比时，反推真实的「多少评级 = 1%」

递减用 `dr_convert()`：**只对越过门槛的那部分打折**，不是整体打折。
精通必须按专精乘系数（`mastery_coeff()`），兽王和射击差近 4 倍。

四类属性公式完全同构，没有任何一处特例：

```
百分比 = 递减后评级 / 分母 + 基线      # 分母 46/44/54/46，来自客户端 __combat_ratings
```

> 以前这里有个坑：`_curve_pct` 里写死了 `+ mastery_base_points(8)`，意思是"所有人
> 都有 8 点基础精通"。实测发现射击和敏锐确实是 8 点，生存和守护是 14 点——
> 多出来的 6 点是天赋。现在 8 点被并进 `spec_stats.mastery`，公式里不再有全局常数。

`flat_source()` 会告诉前端每一项的来路，界面据此标注：

| 值 | 含义 |
|---|---|
| `panel` | 玩家填了面板，精确到这个角色 |
| `spec` | 查表得来，是该专精的默认基线（不含角色自己的天赋选择） |
| `base` | 只有客户端写死的 5% 基础暴击，职业天赋一概没算 |
| `none` | 什么都没有，这一项只有装备部分，会比游戏低 |

悬停属性百分比能看到拆分明细（`装备 23.15% ＋ 天赋 15.00%`），
对不上游戏面板时能立刻判断是装备算错还是天赋没算。

## 基础值的三优先级

`recompute()` 里 base 的来源，优先级从高到低：

1. `panel`——玩家填的面板（`面板 − 首次装备合计`），含天赋
2. `class`——客户端 gt 表（`class_base` + `race_base`），**不含天赋**
3. 空——只显示装备本体

`base_source` 字段会告诉前端当前用的是哪一种，界面上据此标"未含天赋"。

## 天赋这块的现状（重要）

`talents.py` 能把 simc 的 `talents=` 字符串解成「点了哪些节点」，但**没接入计算**：

- `talents.json` 里只有 `classes`（节点表），**没有 `effects`**（法术效果表）
- `stat_bonuses()` 需要 `effects` 参数，目前没有调用方
- `session.py` 没有 `import talents`

原因和后续判断写在 `docs/技术路线.md` 的「已知边界」第 1 条。简单说：能解出来，但算不出
每个天赋给多少属性，而效果数据很难抓（wowhead 给不出 aura 108 的数值）。
现在这部分由 `panel.json` 兜住。

**留着这个模块是因为解码器本身是对的**，一旦找到效果数据源就能直接接上。

## 最容易踩的三个坑（都在 `simc.py` 的注释里详述）

1. **主属性多形态**——`力量/智力` 按职业收敛成一条，否则虚高一倍。
2. **自选槽是预算不是数值**——stat_id 24/25 的 alloc 是一整块，不是属性值。
3. **`redirected_base_stats` 重定向**——套装转化件的属性要按源装备算，不能用自己的表。
